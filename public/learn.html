本课目标

  1. 区分调用成功、数据符合契约、业务结果正确。

这说明应分别检查以下三个边界：

检查边界具体问题通过后仍未证明的事项
调用层是否收到响应？HTTP／SDK状态和模型完成状态如何？返回数据一定符合契约
数据契约层语法能解析吗？对象、字段、类型、枚举、长度等符合约定吗？内容忠于输入、符合业务规则

这里的“调用层”是应用开发的教学划分，不是在复述OSI网络分层。

2. 调用成功：先确认接口发生了什么

在Fetch中，收到404或503响应时，Promise仍可能正常得到Response；应检查状态，而不能只看是否进入catch。Response.ok表示状态码是否在200–299范围。依据：MDN Fetch

还要区分两次调用：

浏览器看到的200、应用调用模型时的200，属于不同位置。健康检查接口200，也不能证明工单分诊已经完成。本仓库的Mock provider是本地函数，并没有第二次远程模型HTTP调用。

部分模型服务即使HTTP为200，也可能返回拒答或因输出长度限制而未完成。适配器应按所用服务的协议检查完成状态，而不把不同厂商字段混为一谈。示例依据：Claude结构化输出中的异常情况

排错习惯：先写明观察的是哪一层、哪个接口、什么状态、是否完整，再判断结果。

3. JSON.parse只解决JSON语法解析

以下文本都属于合法JSON：

合法JSON可以是对象，也可以是数组、字符串、数字、布尔值或null。因此，“JSON.parse没有抛错”仍不足以判断结果是不是你需要的业务对象。

下一步才是验证数据契约，例如：

  • 最外层是否是期望的对象。
  • category是不是允许的枚举值。
  • summary是不是去除空白后仍非空的字符串。
  • missingInformation是不是字符串数组。
  • 长度、数量和额外字段的策略是什么。

JSON Schema可以描述结构与约束，并交给运行时validator检查。Schema本身需要配合校验器执行。依据：JSON Schema入门

注意：字段的“非空”“最多200字符”等局部约束，属于本课的数据契约检查；摘要是否忠于用户输入，属于业务判断。两者不要混称为“语义校验”而省略具体规则。

4. TypeScript的as不会校验外部数据

看一个与工单作业无关的小例子：

输出是：

TypeScript按你的断言看待该值，但原始JSON里的字符串没有被转换成数字。如果继续调用只属于数字的方法，可能在运行时失败。类型断言在编译时被移除，不执行运行时检查。依据：TypeScript Type Assertions

因此，读取外部输入时，可以先把它当unknown，再通过运行时检查逐步确定类型。你可以使用校验库，也可以为简单结构写检查；重点是检查真实数据，并能解释约束。

代码阅读时要问：这个类型是程序验证出来的，还是通过as告诉编译器的？

5. 结构合格与业务正确分别判断

仍以工单分诊为例：

返回情况定位
JSON文本被截断，无法解析数据契约层中的语法问题；同时需要追查是否调用未完成
category为urgent，超出允许枚举数据契约错误
summary只有空格违反字段约束，属于数据契约错误
字段全部合法，但把白屏故障写成新增需求业务内容错误
分类合理，但优先级缺少统一规则需要先定义业务规则，不能凭感觉宣布正确

表中的urgent只是假设错误值，课程契约的category枚举为bug／feature／question。

业务正确性应使用有标准的样例、来源核对或人工评阅等方法验证。在更复杂的系统中，还会进一步建立评测集与评分口径。

一个成功样例可以说明这个样例成功，不足以推出整套应用的可靠性。

6. Prompt、结构化输出、程序校验的分工

机制能帮助解决什么仍需处理什么
Prompt描述任务、输入范围、字段含义、输出约定和缺信息处理模型未按要求作答、任务理解错误
服务端结构化输出能力在服务支持的范围内约束输出结构拒答、截断、支持范围、字段内容是否正确
应用运行时校验按业务契约检查实际收到的数据分类和摘要是否忠于输入
业务评测与复核按样例、规则与证据判断任务结果数据覆盖范围、规则变化及真实使用表现

结构化输出比单纯要求“返回JSON”提供更强的结构约束。具体支持范围和异常以所用服务文档为准，不能把“格式受约束”解释成“内容天然正确”。服务能力示例：Claude Structured Outputs

本课不要求现在接入某一家服务，也不要求为学习这个概念发起收费调用。

五个需要分开记住的判断

判断检查对象
HTTP／SDK调用是否正常响应、状态、错误、完成／拒答状态
JSON语法能否解析文本是否是完整合法JSON
数据是否符合契约对象、字段、类型、枚举、长度与数量
内容是否符合任务与输入一致、规则明确、结论有依据
验证能支持多大范围单个样例、Mock、真实模型或真实使用分别记录

后三个检查不能由HTTP 200自动推出。

常用概念

  • JSON.parse：解析语法，不验证你的业务对象。
  • as：类型断言，不会把字符串变成数字，也不执行运行时校验。
  • unknown：先不假设外部数据的结构，再验证和缩小类型。
  • Schema：描述数据结构与约束；validator负责执行检查。
  • Prompt：表达任务与约定。
  • 结构化输出：服务在支持范围内约束结构；仍要处理异常与业务正确性。
  • Mock：人为固定或模拟的响应，用于工程验证；不能证明模型理解了输入。

类型断言行为见TypeScript官方说明；Fetch状态处理见MDN。

失败分类速查

  • 无法解析JSON：语法或完整性问题，并追查上游完成状态。
  • 未知枚举／字段缺失／空白摘要：数据契约问题。
  • 字段合法但内容答错：业务问题。
  • 规则根本没定义：先补业务规则，再谈正确率。

代码审查四问

  1. 此处数据来自哪里？
  2. 这个类型由什么实际检查支撑？
  3. 无效结果在哪一层被拒绝？
  4. 我亲自验证的结果，能支持多大范围的结论？
