# S1-L02｜超时与取消：把停止信号送到真正工作的地方

**网页主线：直接阅读讲解 → 动手实验 → 随堂练习 → 公开自测 → 复习速记。无需启动项目、安装依赖或提供 API Key。**

本课网页任务：把调用前取消改成调用后取消，预测 started 与 active 的区别。

网页实验范围：四条取消路径与资源计数均由实际异步执行检查。

**选做实操说明：**下面涉及 Node、Python、数据库或 SDK 的环境、命令和完整文件供进阶使用，不是阅读本课的前置条件。


教材已扩写，不代表学习者已经掌握。本课使用 Node 24 本地任务，不调用模型、不产生模型费用。先修：能解释第一课的调用、契约与业务边界。

## 本课目标

- 区分“不再等待”“发出取消信号”“任务实际停止”三件事。
- 写出含调用前取消、执行中取消、截止时间和资源清理的最小实验。
- 根据请求标识与日志判断晚到结果能否更新界面。

## 1. 先看一个你熟悉的故障

用户搜索 A，马上又搜索 B。B 先返回，页面显示 B；随后 A 返回，又覆盖成 A。这里至少有两个问题：旧结果不该更新当前页面，以及旧任务是否应该继续占用资源。

只比较 requestId，可以解决前一个问题，却没有停止后台计算。只调用 abort，也不能假定每个下游都真的停止。我们需要一张具体路径图：

~~~text
React 操作 → 浏览器 fetch → 应用连接/任务 → provider → 上游 HTTP/SDK
                 ↓                ↓             ↓
            取消等待          传递信号        观察并响应
~~~

每条箭头都要有实现和证据。浏览器请求结束不等于外部服务未执行，更不等于没有费用。

## 代码阅读：一次取消怎样走完整条路径

### 先认识三个对象

Controller 是“可以发停止信号的开关”，signal 是“别人能订阅的状态”。把 signal 传给函数不会自动停止函数；工作函数必须检查它，或把它传给支持取消的 API。Promise 只表示未来的结果，也不自带停止能力。

本例的 durationMs 是模拟工作需要的时间，timeoutMs 是允许等待的时间。它们属于两个独立计时器，不能混为同一个变量。stats 的三个计数是观测点，帮助你检查是否真的启动和清理。

### 按输入输出阅读函数

performCancellableWork(100, signal) 输入工作时长与信号，成功返回 done，取消时抛出 signal.reason。先执行 throwIfAborted，意味着已经取消时，started 和 active 都不增加。

runWithDeadline(100, 5, callerSignal) 创建5毫秒的截止开关，再用 AbortSignal.any 合并调用方与期限两个信号。任一方先取消，工作函数就收到同一个停止事件。这个函数的 finally 只负责截止计时器，工作函数自己的 finally 负责工作计时器与监听器，所有权分工清楚。

~~~js
// 这几行只展示核心连接，完整实现见下方文件。
const combinedSignal = AbortSignal.any([
  callerSignal,
  deadlineController.signal,
]);
await performCancellableWork(durationMs, combinedSignal);
~~~

### 跟踪四个场景

|场景|started 的变化|active 最终值|结果|
|---|---|---|---|
|2毫秒工作，100毫秒期限|0变1|0|done|
|100毫秒工作，5毫秒期限|1变2|0|截止异常|
|调用前已取消|保持2|0|取消异常|
|启动后主动取消|2变3|0|取消异常|

reject 只让等待失败。真正使工作计时器不再触发的是 finally 中的 clearTimeout；removeEventListener 则解除这次任务对信号的订阅。少写任意一个，都可能留下多余资源。

### 先自己完成的小检查

先遮住断言，预测第三种场景的 started；再只删掉 throwIfAborted，观察差异。若 active 最终仍是0，也不能证明“没有启动”：要同时检查 started。迁移到真实模型请求时，把这些观测点换成实际调用次数和服务端清理记录。

## 2. 从 Promise.race 推导正确需求

Promise.race 选择最先结算的 Promise，不具有“杀死其他 Promise”的能力。把一个超时 Promise 与模型请求放进去，超时后调用方会先得到错误，但原请求可能仍继续。

所以先定义契约：调用方在期限内得到确定结果；任务支持协作式取消；已经取消时不开始工作；执行后清理 timer 与监听器；取消原因可以定位。deadline 是整个操作的截止时间，不应在每次重试时重新获得完整时长。

AbortController 是信号源，signal 是被观察的对象。abort(reason) 改变信号状态；真正的工作函数决定如何释放资源。对不支持取消的外部系统，只能停止后续消费并记录仍待确认的执行状态。

## 3. 分步实验：先实现可观察的本地工作

**选做本地验证：**从仓库根目录运行下面的文件。Windows 默认 Node 较旧时，用 scripts/run.ps1 tutorial S1-L02；正常 Node 24 可直接运行 node examples/tutorials/S1-L02.mjs。

先读 performCancellableWork 的顺序：检查已经取消 → 注册监听 → 设置计时 → 无论成功失败都清理。这个先后顺序决定“已取消的输入”是否还会启动任务。

### 完整实操文件：S1-L02.mjs

~~~js file=S1-L02.mjs
import assert from "node:assert/strict";

// 本课只有两个计时器角色：工作计时器模拟任务，截止计时器限制总等待时间。
const taskStatistics = {
  started: 0,
  active: 0,
  cleaned: 0,
};

async function performCancellableWork(durationMs, signal) {
  // 已取消就直接抛出原因；不能先增加计数、发请求，再检查取消。
  signal.throwIfAborted();

  taskStatistics.started += 1;
  taskStatistics.active += 1;

  let workTimer;
  let handleAbort;

  try {
    await new Promise((resolve, reject) => {
      handleAbort = () => reject(signal.reason);
      signal.addEventListener("abort", handleAbort, { once: true });
      workTimer = setTimeout(resolve, durationMs);
    });

    return "done";
  } finally {
    // resolve 和 reject 最终都会经过这里，避免任务结束后仍保留计时器和监听器。
    clearTimeout(workTimer);
    signal.removeEventListener("abort", handleAbort);
    taskStatistics.active -= 1;
    taskStatistics.cleaned += 1;
  }
}

async function runWithDeadline(
  durationMs,
  timeoutMs,
  callerSignal = new AbortController().signal,
) {
  const deadlineController = new AbortController();
  const deadlineTimer = setTimeout(() => {
    deadlineController.abort(new Error("DEADLINE_EXCEEDED"));
  }, timeoutMs);

  // 任意一方取消都会使 combinedSignal 取消，并保留最先发生的原因。
  const combinedSignal = AbortSignal.any([callerSignal, deadlineController.signal]);

  try {
    return await performCancellableWork(durationMs, combinedSignal);
  } finally {
    clearTimeout(deadlineTimer);
  }
}

// 场景一：工作比期限短，正常完成。
assert.equal(await runWithDeadline(2, 100), "done");

// 场景二：工作比期限长，真正的工作函数收到取消。
await assert.rejects(runWithDeadline(100, 5), /DEADLINE_EXCEEDED/);

// 场景三：调用之前已取消，任务根本不应该启动。
const preCancelledController = new AbortController();
preCancelledController.abort(new Error("CALLER_CANCELLED"));
const startedBeforeCall = taskStatistics.started;
await assert.rejects(
  runWithDeadline(100, 500, preCancelledController.signal),
  /CALLER_CANCELLED/,
);
assert.equal(taskStatistics.started, startedBeforeCall);

// 场景四：任务启动后，调用方主动取消。
const inFlightController = new AbortController();
const pendingTask = runWithDeadline(100, 500, inFlightController.signal);
inFlightController.abort(new Error("CALLER_CANCELLED"));
await assert.rejects(pendingTask, /CALLER_CANCELLED/);

assert.equal(taskStatistics.active, 0);
assert.equal(taskStatistics.cleaned, taskStatistics.started);
console.log("success / deadline / pre-cancel / in-flight cancel: passed");
console.log("active=0; every started task cleaned");
~~~
~~~text expect=S1-L02.mjs
success / deadline / pre-cancel / in-flight cancel: passed
active=0; every started task cleaned
~~~

实验用确定的断言判定结果，不比较“应该恰好耗时 5 毫秒”。计时器受调度影响，真实系统也会有误差。这里证明了本地实现响应取消、清理资源；没有证明任何服务商会停止计费。

## 4. 沿着代码读一遍数据流

runWithDeadline 持有整体 deadline，performCancellableWork 不自行重置期限。AbortSignal.any 把用户取消和截止时间合成一个信号；最先触发的原因会被传下去。工作函数开头 throwIfAborted，使预取消用例的 started 不增加。

finally 同时覆盖正常、超时和主动取消。只在 catch 清理会漏掉正常路径；只清 timer 不清监听器可能把回调保留在长期存活的信号上。实验的 active 和 cleaned 是白盒观测，不是生产指标的完整实现。

为什么不把所有异常改成 USER_CANCELLED？因为超时、用户撤回和上游失败会导致不同提示、重试与运营判断。实际适配器应保留原因链，再映射为稳定的应用错误，不直接把内部堆栈返回给用户。

## 5. 故障注入与最小修复

第一步，暂时删掉 throwIfAborted。预取消断言可能失败，或任务一直等到另一个期限：事件监听器不会补发已经发生的 abort 事件。最小修复是保留调用前检查，不是扩大超时时长。

第二步，删去 finally 中的 active--。功能返回可能仍正确，但资源断言失败，说明“拿到错误”与“工作被清理”是不同主张。恢复后再跑全部四条用例。

第三步，把 performCancellableWork 换成一个忽略 signal 的函数，说明为何 runWithDeadline 的信号合成也救不了它。本课按时结束依赖工作函数响应信号；S2-L02进一步实现调用方的有限等待。项目中还要在 HTTP/SDK、数据库或子任务真正等待的位置接入取消能力。

## 6. 迁移到工单项目

先画出 /api/triage 到 provider 的调用路径，标出 signal 的创建、转交、观察位置。客户端断开后服务端怎样收到通知，应按实际 HTTP 框架测试，不凭前端按钮推断。请求已经结束时，不向同一响应再写成功结果。

前端另外用 runId 拒绝旧结果。即使上游不支持取消，过期任务也不能覆盖当前任务。向用户区分“已请求取消”“本地执行已终止”“外部副作用待确认”，不要把未知状态伪装成成功回滚。

## 单页速记

- race 停止等待，不自动停止另一项工作。
- signal 需一路传递并被实际操作消费。
- 预取消先检查，结束统一清理，原因分开记录。
- 请求标识保护 UI；取消控制资源；外部执行与费用另行核验。
