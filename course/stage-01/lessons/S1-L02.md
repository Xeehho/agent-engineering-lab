## 本课目标

- 区分超时、主动取消与上游故障
- 让取消信号沿数据流传播
- 验证资源是否释放

## 1. 区分超时、主动取消与上游故障

用户切换页面后，旧请求仍占用模型并发；页面显示“已取消”不等于后台已停止。超时是达到截止时间，主动取消是调用方撤回，网络错误是另一类原因。先为每种情况定义错误码、UI 状态和日志字段，再讨论实现。不要把所有失败都返回 HTTP 200 加空结果。

## 2. 让取消信号沿数据流传播

AbortController 发出信号，需要下游操作接收并响应。Promise.race 可以停止等待，却不会自动终止输掉竞赛的任务。浏览器断开到服务端的传播还取决于服务器如何处理连接事件，不能只给浏览器 fetch 加 signal 就宣布上游已取消。演示只证明协作式任务响应了本地信号。

## 3. 验证资源是否释放

用已经取消的信号、执行中取消、截止时间到达、刚完成时取消四种顺序验证。检查是否调用过 provider、监听器与 timer 是否清理、晚到响应会不会覆盖新状态。请求取消不保证服务商未计费；计费与上游执行状态需服务协议和实际证据。

## 实验：停止等待与停止工作

先预测输出，再运行并修改一个条件。这是教学用的 JavaScript 机制演示，不是真实模型、数据库、协议 SDK 或生产系统。

~~~js
const controller = new AbortController();
let working = true;
const task = new Promise(resolve => {
  const timer = setTimeout(() => { working = false; resolve("完成"); }, 80);
  controller.signal.addEventListener("abort", () => {
    clearTimeout(timer); working = false; resolve("已响应取消");
  }, { once: true });
});
controller.abort();
console.log(await task, "仍在工作:", working);
~~~

观察方向：应看到已响应取消和 false。删去监听器后再比较：abort 本身不会替你清理任意任务。

提示：观察清理 timer 的代码实际位于哪里。
