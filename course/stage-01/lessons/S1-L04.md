# S1-L04 测试通过，到底证明了什么

## 先说我们要解决什么问题

AI 帮你写了代码并说“测试全绿，可以上线”。如果测试中的模型只是返回固定答案，这句话缺少哪一段证据？

## 先把概念讲清楚

证据是支持某个具体结论的可检查记录。Mock（替身）用固定行为代替外部组件，让本地检查可重复；它不能证明那个真实组件也有相同行为。验收要先写结论，再问证据是否覆盖结论。

区分三件事：软件在特定输入下按预期工作；真实服务能够接通；真实任务的效果达到目标。一次成功响应通常只证明某次接通，不能直接证明总体质量。

## 名字与字段从哪里来

|名字或字段|来源与含义|
|---|---|
|claim|想支持的结论，课堂字段|
|kind / passed|证据类型与该项是否通过，课堂约定|
|controlled / real|本课证据分类，不是任何测试框架的保留字|
|canClaimReal|课堂判断函数；真实验收还需要任务、环境、版本和日期|

## 先读这个最小例子

在网页“动手实验”直接运行。先读输入，再找检查和输出；assert 是课堂提供的检查函数，不是模型能力。

~~~js
const evidence = [
  { kind: "controlled", passed: true },
  { kind: "real", passed: false },
];
function canClaimReal(rows) {
  return rows.some((row) => row.kind === "real" && row.passed);
}
console.log("本地检查通过：", evidence[0].passed);
console.log("可声称真实接通：", canClaimReal(evidence));
assert.equal(canClaimReal(evidence), false);
~~~
## 运行结果与逐步解释

~~~text
本地检查通过： true
可声称真实接通： false
~~~

数组第一项通过，支持“某次受控检查通过”。函数主动寻找 real 且 passed 的记录，没有就返回 false。把第二项手动改为 true 只改了声明，仍需保留真实请求的脱敏记录；代码不能把自报数据变成可信证据。

## 在网页里完成三件小事

1. 为“取消后UI无晚到文本”写一个最小受控验收。
2. 给真实接通证据增加你认为必需的版本和日期。
3. 列出本地、真实接通、质量评测各不能证明的一件事。

## 1. 从一句不能验收的话开始

“我让 AI 把接口写完了，测试全绿。”这里没有说明测试检查什么、用什么 provider、运行在哪个 commit，也没有说明测试是否真的执行了关键分支。

先把主张拆开：合法输入得到结果；缺少字段被拒绝；输出不合约时不显示成功；超时有截止时间；取消传到工作操作；旧响应不更新 UI。这些主张应分别对应输入、预期、实际和观测点。

截图能证明某个时刻页面出现了文字，不能独自证明服务端停止、权限隔离或模型准确。代码存在能说明实现意图，运行证据才能说明那条路径被实际触发。

## 代码阅读：报告里的 passed 从哪里来

### 两个函数分别负责什么

parseNonNegativeCount 输入 JSON 文本，成功返回非负整数，失败抛出原因。runContractCase 输入一条事先定义的用例，实际调用前者，再比较 actual 与 expected。业务逻辑和报告逻辑分开后，你可以单独定位“实现错了”还是“评分规则错了”。

expected 是需求的表达，必须先写。actual 来自真正执行的返回值或异常。若直接把 expected 复制给 actual，再漂亮的报告也没有验证价值。

### 用一个输入走完整条路径

~~~js
const jsonText = '{"count":"2"}';
const parsedValue = JSON.parse(jsonText);
console.log(typeof parsedValue.count); // string
console.log(Number.isInteger(parsedValue.count)); // false
~~~

JSON.parse 没有把双引号中的2转成整数。parseNonNegativeCount 因此抛出 INVALID_COUNT，runContractCase 捕获异常并把错误码记录为 actual。预期也恰好是 INVALID_COUNT，所以这条拒绝用例通过；通过的含义是“正确拒绝了非法数据”。

|用例|实际运行得到|为何通过|
|---|---|---|
|normal|数字2|与预期数字相同|
|string|INVALID_COUNT|正确拒绝字符串|
|null|NOT_OBJECT|在读取字段之前拒绝外层值|
|negative|INVALID_COUNT|正确拒绝负数|

### 怎样读断言

assert.equal(actual, expected) 不相等就抛异常，进程失败。这里汇总通过数，是为了让脚本在任何一条失败时退出非零；控制台打印只是给人看。之后要追查失败原因，应查看 evidenceRows 中的具体输入与实际结果，而非只盯住总数。

本例将返回值和错误码放在同一 actual 字段，是因为数字与错误字符串能清楚区分。更复杂的系统应使用结构化结果，例如 ok/data 或 ok/code，避免“返回的字符串刚好等于错误码”。

### 带提示的练习

先增加 count=0 的用例，不改实现，预测是否通过。再增加损坏 JSON，决定是否保留原始解析错误还是映射统一错误码。最后删除负数检查，保存失败记录，并根据契约修复，不能改 expected 迎合错误实现。

## 2. 证据表必须能追到版本

至少记录 caseId、commit、环境、输入、预期、实际、结论与限制。真实模型另有 provider/model/Prompt版本/日期/usage，未知就写未知。不要把无法获取的字段填成 0 或“已经验证”。

环境是结论的一部分。内存 Map 的去重不能当作数据库跨实例保证；本地固定输出不能当成模型理解输入。测试数量也不是能力评分，同一主张重复一百次可能仍只覆盖一个边界。

## 3. 跟着做：生成一份真实的本地检查报告

**选做本地验证：**这个示例验证一个与工单作业无关的计数契约，让你观察报告来自实际运行，而不是先填写 passed。运行 node examples/tutorials/S1-L04.mjs。

### 完整实操文件：S1-L04.mjs

~~~js file=S1-L04.mjs
import assert from "node:assert/strict";

// 被测逻辑：从外部 JSON 文本读取非负整数，不负责工单业务。
function parseNonNegativeCount(jsonText) {
  const parsedValue = JSON.parse(jsonText);
  const isObject =
    parsedValue !== null &&
    typeof parsedValue === "object" &&
    !Array.isArray(parsedValue);

  if (!isObject) {
    throw new Error("NOT_OBJECT");
  }
  if (!Number.isInteger(parsedValue.count) || parsedValue.count < 0) {
    throw new Error("INVALID_COUNT");
  }
  return parsedValue.count;
}

// 预期先按契约写好；actual 必须来自实际执行，不能复制 expected。
const testCases = [
  { id: "normal", input: '{"count":2}', expected: 2 },
  { id: "string", input: '{"count":"2"}', expected: "INVALID_COUNT" },
  { id: "null", input: "null", expected: "NOT_OBJECT" },
  { id: "negative", input: '{"count":-1}', expected: "INVALID_COUNT" },
];

function runContractCase(testCase) {
  let actualResult;
  try {
    actualResult = parseNonNegativeCount(testCase.input);
  } catch (error) {
    actualResult = error.message;
  }

  return {
    ...testCase,
    actual: actualResult,
    passed: Object.is(actualResult, testCase.expected),
    environment: "Node/local",
    provider: "none",
  };
}

const evidenceRows = testCases.map(runContractCase);
assert.equal(evidenceRows.filter((row) => row.passed).length, testCases.length);

for (const row of evidenceRows) {
  console.log(row.id + ": " + row.passed + " (" + row.actual + ")");
}
console.log("scope: four local contract cases; no model accuracy claim");
~~~
~~~text expect=S1-L04.mjs
normal: true (2)
string: true (INVALID_COUNT)
null: true (NOT_OBJECT)
negative: true (INVALID_COUNT)
scope: four local contract cases; no model accuracy claim
~~~

先运行未修改版本。然后把 count < 0 的拒绝删掉：negative 用例将失败。不要修改 expected 去迎合错误实现，先回到“计数允许负数吗”这个需求。若需求真的变化，须同时修改契约、用例与说明。

## 4. 用一次失败证明你理解了路径

一个可审阅复盘包含：原始现象、复现输入、所在版本、最初假设、支持/否定假设的证据、定位、最小改动和回归。它不需要写成日志流水账，而要让读者理解为什么这个改动解决这个问题。

例如字符串 "2" 被错误接收，不要直接归因于模型。先检查 JSON.parse 后实际类型，再看运行时 validator。若 AI 建议加 as Count，这不增加校验。你应要求它在接收外部值的位置加入可执行约束，并验证正常路径没有被破坏。

## 6. 代码审阅演练

按这个顺序问自己：输入从哪里进入；数据何时从 unknown 被收窄；错误在哪层被转成响应；资源在哪条结束路径释放；同一结果能否在固定版本复现。若回答只能是“AI说这样可以”，该处还没有通过本人理解检查。

在项目自述中使用准确表述：“已验证四条本地契约用例，真实模型效果待测”，而不是“应用准确率100%”。一次失败被正确处理也是有价值的证据，不应为了展示漂亮而删除。

## 练习与验收

1. 为同一个功能写三条独立主张，并写清哪种证据足够、哪种不够。

3. 补齐项目提交模板，说明 AI 生成、本人判断、本人运行和仍待验证的范围。

## 单页速记
