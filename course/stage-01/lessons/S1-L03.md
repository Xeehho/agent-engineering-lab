## 1. 区分字节、消息与任务事件

流式传输一次 read 得到的 chunk 不是完整业务事件：一个事件可能被拆开，多个事件也可能合并到一个 chunk。UTF-8 字符也可能跨 chunk，要使用流式解码器并缓存未完成的消息。SSE 的空行分隔与字段语法需按协议解析；课堂事件列表不是网络解析器。

## 2. 设计可验证的 UI 状态机

从 idle 到 running，再到 succeeded、failed 或 cancelled，终态之后拒绝旧 delta。连接还开着不等于任务还执行，拿到部分文字也不等于完整结果可提交。用 requestId / runId 关联事件；重连或重放还需 eventId、去重和恢复约定。不要用一个 loading 布尔值表示所有状态。

## 3. 选择传输与处理失败

原生 EventSource 的用法与 fetch 流式读取不同；需要 POST 请求体或特定头时，应依据接口契约选传输。HTTP 头写出前可以返回错误状态；写出后一般要用协议内 error 事件和日志说明，不能假装重新发送一份 JSON 500。取消按钮还要接上服务端取消路径。

## 实验：终态之后的文字能进来吗？

先预测输出，再运行并修改一个条件。这是教学用的 JavaScript 机制演示，不是真实模型、数据库、协议 SDK 或生产系统。

~~~js
let state = "running", text = "";
for (const event of [{type:"delta",text:"订单"}, {type:"cancelled"}, {type:"delta",text:"旧结果"}]) {
  if (state !== "running") { console.log("忽略晚到事件", event.type); continue; }
  if (event.type === "delta") text += event.text;
  else state = event.type;
}
console.log({state, text});
~~~

观察方向：取消后的 delta 被忽略，text 只有订单。这只是 reducer 示例，未验证真实 SSE、断网和重连。

提示：先检查是否处于终态，再消费事件。
