## 本课目标

- 建立服务与用户两条信任线
- 绑定资源并限制输出
- 考虑工具描述与输出污染

## 1. 建立服务与用户两条信任线

确认 Server 来源、版本、维护者与可执行代码范围，同时确认当前用户能访问的具体资源。服务可信不代表每个用户都可读全部工单。远程服务的认证/授权需遵循所选传输与规范要求；不能把另一个服务收到的凭证不加校验地透传。

## 2. 绑定资源并限制输出

ticketId 本身不是权限证明，模型生成的 tenantId 也不是当前租户。服务端从认证上下文得到租户，查询时限定资源范围，并限制返回字段、记录数和内容大小。缓存键至少覆盖影响结果的身份、权限范围、资源与版本，避免跨租户复用。

## 3. 考虑工具描述与输出污染

工具元数据或返回内容也可能夹带诱导指令。Host 应区分描述、用户意图与外部数据；危险操作保持程序限制与具体确认。新增服务器意味着新的可执行能力和数据流，应在测试环境审查它能访问什么，不能为跑通示例而关闭安全检查。

## 实验：相同工单编号，不同租户

先预测输出，再运行并修改一个条件。这是教学用的 JavaScript 机制演示，不是真实模型、数据库、协议 SDK 或生产系统。

~~~js
const tickets = [{tenant:"A",id:"T-1",text:"A 私有"},{tenant:"B",id:"T-1",text:"B 私有"}];
function readTicket(auth, id) {
  return tickets.find(t => t.tenant === auth.tenant && t.id === id);
}
console.log(readTicket({tenant:"A"},"T-1"));
console.log("身份仅为合成演示，生产中来自认证中间件");
~~~

观察方向：只能找到 A 的记录。不要把 auth 改成由模型传入后还声称权限已保障。

提示：认证身份必须来自可信服务端路径。
