## 本课目标

- 区分协议错误与工具业务失败

## 1. 从发现开始验证

服务监听端口只证明进程存在。实际接入需依据所选修订验证发现机制、工具描述、输入 Schema、调用结果和错误形态。工具发现缓存也可能过期；记录客户端看到的版本与可用工具，避免客户端仍按旧结构提交参数。不要把健康检查成功当作协议互通。

## 2. 分清 stdio 与 HTTP 部署假设

stdio 由宿主启动进程并通过标准流通信时，普通日志不能混入协议输出；HTTP 传输还要考虑端点认证、代理、连接与超时。传输支持随版本变化，按照实际 SDK 文档实现，别把 SSE 示例套在所有修订上。两种方式都仍需要业务层的期限、大小上限和取消处理。

## 3. 区分协议错误与工具业务失败

未知方法、无效消息属于协议处理的问题；工单不存在或查询被业务拒绝是另一层的失败。客户端需要按真实结果处理，不能只因为收到了一个 JSON 就当工具成功。对每类失败记录请求关联、可重试性及安全错误信息，避免将内部堆栈或密钥回给模型。

## 实验：合法消息与成功业务不同

先预测输出，再运行并修改一个条件。这是教学用的 JavaScript 机制演示，不是真实模型、数据库、协议 SDK 或生产系统。

~~~js
const responses = [
 {transport:"ok",business:{ok:true,data:{id:"T-42"}}},
 {transport:"ok",business:{ok:false,code:"NOT_FOUND"}}
];
for (const r of responses) console.log(r.transport, "业务成功:",r.business.ok);
console.log("这是教学包裹，不是 MCP 标准返回结构");
~~~

观察方向：两条传输观察相同，业务结论不同。真实协议结果需按 SDK 与修订检查。
