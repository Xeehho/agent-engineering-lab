# S3-L01｜MCP 的边界：Host、Client、Server

教材状态：已编写，可提前学习；不代表学习者已作答或通过考试。
阶段：03 MCP 互操作与信任。先修：02 的工具契约与权限。

## 本课目标

- 按角色画部署图
- 区分能力与内容
- 选择何时引入协议

## 1. 按角色画部署图

Host 是使用模型与工具的 AI 应用，Client 是 Host 内与服务对接的协议组件，Server 提供工具等能力。它们是职责划分，不要求每个角色都是独立机器。MCP 不是模型，也不是 Agent 推理算法；把工具暴露为 MCP，不会自动获得规划、正确率或业务授权。

## 2. 区分能力与内容

工具是可调用能力，资源是可读取上下文，提示模板用于复用交互；不要把任何一段可检索文字都叫作工具。先说明调用方发现什么、传什么、得到什么，再选 SDK。协议与 SDK 会演进，固定协议修订和 SDK 版本，按对应文档核对发现、能力协商和结果结构，不能混用旧教程与新版实现。

## 3. 选择何时引入协议

单服务内部函数调用可以很简单；需要跨应用接入、多语言工具服务或统一发现时，MCP 才可能降低集成成本。先写一份 getTicket 的业务契约，再把它适配到 MCP。课堂 JSON 只是角色映射示意，不构成与真实 MCP 客户端互通的测试。

## 动手验证

先写预测，再运行，最后修改一个条件观察反例。不要把网页机制演示当成真实基础设施验证。

## 实验：把角色和业务工具分开

先预测输出，再运行并修改一个条件。这是教学用的 JavaScript 机制演示，不是真实模型、数据库、协议 SDK 或生产系统。

~~~js
const deployment = {host:"研发助手",client:"Host 内协议组件",server:"知识工具服务"};
const tool = {name:"getTicket",input:{ticketId:"T-42"}};
console.log(deployment);
console.log("业务能力:", tool);
console.log("这不是 MCP wire message");
~~~

观察方向：部署角色、业务契约与实际协议消息是三个层次。

提示：不要把示意对象直接冒充规范规定的消息。

## 本阶段验收边界

- 协议修订、SDK 与运行环境明确
- 真实发现、调用、错误与取消可复现，网页模拟不计互通
- 身份与租户权限不来自模型参数
- 日志通道、返回上限、服务来源与凭证作用域可解释
