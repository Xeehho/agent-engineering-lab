## 本课目标

- 把确认设计成状态与证据
- 设计暂停、恢复与取消的产品语义
- 处理列表、详情与实时事件的一致性

## 1. 把确认设计成状态与证据

AI 建议发送回复时，页面应展示接收对象、具体内容、影响范围和执行来源，用户确认后再让后端验证绑定内容与版本。确认不是随便一个 confirm 按钮；过期、权限变化、内容修改都可能使它失效。只在前端禁用操作挡不住伪造请求。

## 2. 设计暂停、恢复与取消的产品语义

暂停可能只阻止后续步骤，并不撤销已经完成的写入。用户刷新后，应从服务读取持久任务状态，再恢复事件观察；不能靠 localStorage 中的 running 一直展示执行中。区分“已请求取消”“执行已终止”“已完成副作用待处理”，使反馈与真实行为对应。

## 3. 处理列表、详情与实时事件的一致性

列表快照与事件可能乱序到达，用任务版本或单调事件序号防止旧快照覆盖新状态。按 taskId 隔离多个并行任务，错误事件保留可操作的恢复提示。提供键盘可达、屏幕阅读提示与明确进度，不用不断闪烁的全文替换模拟流式体验。

## 实验：旧快照不应覆盖新状态

先预测输出，再运行并修改一个条件。这是教学用的 JavaScript 机制演示，不是真实模型、数据库、协议 SDK 或生产系统。

~~~js
let task = {version:4,status:"waiting_approval"};
const updates = [{version:3,status:"running"},{version:5,status:"succeeded"}];
for (const update of updates) {
  if (update.version > task.version) task = update;
  else console.log("忽略旧快照",update.version);
}
console.log(task);
~~~

观察方向：版本 3 被忽略，最终采用版本 5；真实多源事件仍需统一版本约定。

提示：别用消息到达顺序替代业务版本。
