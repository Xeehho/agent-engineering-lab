# S4-L03 人工审批与 React 任务界面

**网页主线：直接阅读讲解 → 动手实验 → 随堂练习 → 公开自测 → 复习速记。无需启动项目、安装依赖或提供 API Key。**

本课网页任务：只改 ticket、text 或 version，逐一验证旧签名不能授权新动作。

网页实验范围：实际 Web Crypto HMAC，消费记录只在本次内存，没有真实发送。

**选做实操说明：**下面涉及 Node、Python、数据库或 SDK 的环境、命令和完整文件供进阶使用，不是阅读本课的前置条件。


“用户点过同意”必须落到一个不可混淆的具体动作。本课执行 HMAC 参数绑定与单次消费，认证上下文是合成的，防重放集合只在内存，未提供生产持久审批；不代表学习者已掌握。

## 1. 审批的对象是什么

界面展示“向 T-42 发送回复：已修复”，用户确认后，模型把内容改成“请提供密码”。若服务端只检查 approved=true，确认就被借给了另一个动作。

审批至少绑定主体、任务、动作类型、资源、完整参数摘要、任务版本、期限与 nonce。用户应看到这些内容的可理解摘要；服务端在执行前重新校验。UI 禁用按钮只改善交互，不能替代最终检查。

## 代码阅读：确认不是一个可以到处复用的 true

### 签名和摘要的区别

摘要把内容映射成固定长度值；HMAC 还使用服务端密钥，持有密钥的一方才能为新内容生成有效签名。签名保护“这份载荷未被改动”，不证明用户已经理解并批准，也不能替代真实登录与权限。

serializeApproval 固定字段与顺序；issueApproval 生成 payload 与 mac；executeApprovedAction 在执行前重新计算签名并比对，再检查业务绑定。

### 依次读六道检查

1. 接收到的签名与重新计算值一致。
2. 当前主体与批准主体一致，且当前仍有发送权限。
3. 当前动作序列化后与批准载荷完全相同。
4. 当前时间小于 expires；等于到期时间也拒绝。
5. nonce 尚未消费。
6. 记录消费后，才接受这一动作。

~~~js
if (serializeApproval(currentAction) !== approvalToken.payload) {
  throw new Error("CHANGED_ACTION");
}
~~~

这道检查把 T-42、正文、任务版本等绑定在同一个确认上。确认后换工单或改正文，都必须重新确认。

### 追踪测试数据

原动作在时间10执行有效；改成T-99被拒绝，Bob复用被拒绝，时间100到期被拒绝。成功执行一次后，相同 nonce 再执行被判重放。签名密钥与 consumedNonces 都只在进程内，所以重启后防重放状态会丢失；本例也没有真正发送消息。

### 带提示的练习

先指出哪一条检查拦住“只改正文”。再把 nonce 消费迁入数据库事务，思考消费成功、发送失败如何重试。React 要展示服务端提案，确认时引用提案ID与版本，不能由浏览器直接提交一个 approved=true 的新正文。

## 2. 可执行的绑定实验

### 完整实操文件：S4-L03.mjs

~~~js file=S4-L03.mjs
// 审批的内容、身份、版本和期限全部参与绑定；本例不发送真实消息。
import assert from "node:assert/strict";
import { createHmac, randomBytes, timingSafeEqual } from "node:crypto";
const signingKey = randomBytes(32);
const consumedNonces = new Set();
// 固定字段顺序，不能接受任意形状对象作为审批契约。
// 固定字段及顺序，生成审批签名和执行比对使用的同一份字节内容。
function serializeApproval(action) {
  return JSON.stringify({
    subject: action.subject,
    task: action.task,
    version: action.version,
    action: action.action,
    ticket: action.ticket,
    text: action.text,
    expires: action.expires,
    nonce: action.nonce,
  });
}
const computeSignature = (serializedPayload) =>
  createHmac("sha256", signingKey).update(serializedPayload).digest();
// 把展示给审批人的动作序列化并签名；实际登录审批流程尚未接入。
function issueApproval(action) {
  const serializedPayload = serializeApproval(action);
  return {
    payload: serializedPayload,
    mac: computeSignature(serializedPayload).toString("base64url"),
  };
}
// 依次检查签名、身份、参数、期限与重放，全部通过才接受执行。
function executeApprovedAction(
  authenticatedUser,
  currentAction,
  approvalToken,
  currentTime,
) {
  const receivedSignature = Buffer.from(approvalToken.mac, "base64url"),
    expectedSignature = computeSignature(approvalToken.payload);
  if (
    receivedSignature.length !== expectedSignature.length ||
    !timingSafeEqual(receivedSignature, expectedSignature)
  ) {
    throw new Error("BAD_SIGNATURE");
  }
  const approvedAction = JSON.parse(approvalToken.payload);
  if (
    approvedAction.subject !== authenticatedUser.subject ||
    !authenticatedUser.canSend
  ) {
    throw new Error("FORBIDDEN");
  }
  if (serializeApproval(currentAction) !== approvalToken.payload) {
    throw new Error("CHANGED_ACTION");
  }
  if (currentTime >= approvedAction.expires) {
    throw new Error("EXPIRED");
  }
  if (consumedNonces.has(approvedAction.nonce)) {
    throw new Error("REPLAY");
  }
  consumedNonces.add(approvedAction.nonce);
  return { sent: true, ticket: approvedAction.ticket };
}
const action = {
  subject: "alice",
  task: "task-1",
  version: 7,
  action: "send_reply",
  ticket: "T-42",
  text: "已修复",
  expires: 100,
  nonce: "approval-1",
};
const authenticatedUser = { subject: "alice", canSend: true };
const approvalToken = issueApproval(action);
assert.throws(
  () =>
    executeApprovedAction(
      authenticatedUser,
      { ...action, ticket: "T-99" },
      approvalToken,
      10,
    ),
  /CHANGED/,
);
assert.throws(
  () =>
    executeApprovedAction({ subject: "bob", canSend: true }, action, approvalToken, 10),
  /FORBIDDEN/,
);
assert.throws(
  () => executeApprovedAction(authenticatedUser, action, approvalToken, 100),
  /EXPIRED/,
);
assert.deepEqual(executeApprovedAction(authenticatedUser, action, approvalToken, 10), {
  sent: true,
  ticket: "T-42",
});
assert.throws(
  () => executeApprovedAction(authenticatedUser, action, approvalToken, 11),
  /REPLAY/,
);
const forged = {
  ...approvalToken,
  payload: approvalToken.payload.replace("已修复", "请转账"),
};
assert.throws(
  () => executeApprovedAction(authenticatedUser, action, forged, 10),
  /SIGNATURE/,
);
console.log("changed action / wrong subject / expired / replay / tamper: rejected");
console.log("one exact approved action accepted; no real message sent");
~~~
~~~text expect=S4-L03.mjs
changed action / wrong subject / expired / replay / tamper: rejected
one exact approved action accepted; no real message sent
~~~

## 3. 从实验迁移到持久审批

生产中密钥由服务管理并支持轮换，nonce 消费与业务写入要在事务内，重试返回幂等结果。内存 Set 在重启后清空，而且与外部发送不原子，因此本例只能证明本次进程内检查。不要把它直接接到真实发送并称已防重放。

可设计 approvals 表保存 task、version、payload_hash、approver、expires、status。执行器通过条件 UPDATE 消费待批准记录，确认角色与当前资源权限，再提交业务事件。多人审批还需要人数、职责分离与撤回规则。

## 4. React 界面的数据流

服务端返回 proposalId、taskVersion 和展示字段。界面展示对象、操作与内容，确认请求只引用服务端提案，不让浏览器重新提交任意“已批准”的正文。等待期间内容变化，旧提案明确失效并重新确认。

将 sending、awaiting_approval、running、succeeded 分开。用户刷新后通过 taskId 拉取服务端状态，不能只靠 localStorage 的 approved=true。按钮提交重复时使用稳定意图键，加载态不等于幂等保障。

旧版本任务事件到达时忽略；审批失败时显示具体可恢复原因，例如提案已更新或审批过期。不要把服务器拒绝改成“用户取消”，这会误导审计与排错。

## 故障练习与项目迁移

去掉 text 绑定，构造确认后换正文；去掉 subject，构造跨用户复用；重启进程，说明 Set 为什么不能承担持久防重放。修改任务版本后验证旧审批失效。

项目练习：实现持久审批记录与 React 预览卡片，提交两窗口竞争、重复点击、刷新恢复、参数变更、过期与撤权案例。老师验收的是服务端拒绝证据，不能只展示按钮变灰。

## 单页速记

- 确认绑定具体动作、主体、参数、版本与期限。
- 签名不替代认证，按钮不替代授权。
- 防重放与副作用要有持久原子边界。
- 界面区分提案、批准、执行中与真实完成。
