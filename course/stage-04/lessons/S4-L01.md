# S4-L01 持久任务：task、run 与 attempt

页面刷新后，任务仍在；工作进程崩溃后，下一次执行能接着判断。这是本课的目标。实验使用文件 SQLite 和版本条件更新，不是生产分布式压测，不代表学习者已掌握。

## 1. 给三个 ID 各自的职责

task 是用户要解决的业务目标；run 是一次编排执行，可因重新规划而更换；attempt 是某一步的具体尝试。模型返回错误后重试，应增加 attempt，不能偷偷创建一个全新 task 来绕过总预算。

状态放在哪里也有区别。React state 负责当前展示；服务端内存能跨组件但不能跨进程重启；持久数据库保存可恢复事实。把一份 UI 状态整个 JSON 化保存，并不自动得到正确的状态机，需要定义谁允许从哪个状态转到哪个状态。

本课选 queued → running → succeeded/failed/cancelled，终态不再变更。重试创建新的 attempt，仍受任务总预算约束；本实验先验证最小任务版本与事件原子性。

## 2. 建表并执行状态转换

~~~js file=S4-L01.mjs
import assert from "node:assert/strict";
import { DatabaseSync } from "node:sqlite";
import { mkdtempSync,rmSync,rmdirSync } from "node:fs";
import { tmpdir } from "node:os";
import { join } from "node:path";
const dir = mkdtempSync(join(tmpdir(),"agent-task-"));
const path = join(dir,"tasks.sqlite");
let db = new DatabaseSync(path);
db.exec("CREATE TABLE tasks(id TEXT PRIMARY KEY,state TEXT,version INTEGER); CREATE TABLE events(task_id TEXT,version INTEGER,state TEXT,PRIMARY KEY(task_id,version))");
db.prepare("INSERT INTO tasks VALUES(?,?,?)").run("task-1","queued",0);
const allowed = {queued:["running","cancelled"],running:["succeeded","failed","cancelled"]};
function transition(id,expectedVersion,to) {
  db.exec("BEGIN IMMEDIATE");
  try {
    const row = db.prepare("SELECT * FROM tasks WHERE id=?").get(id);
    if (!row || row.version !== expectedVersion) throw new Error("STALE_VERSION");
    if (!allowed[row.state]?.includes(to)) throw new Error("ILLEGAL_TRANSITION");
    const changed = db.prepare("UPDATE tasks SET state=?,version=version+1 WHERE id=? AND version=?")
      .run(to,id,expectedVersion);
    if (changed.changes !== 1) throw new Error("CONFLICT");
    db.prepare("INSERT INTO events VALUES(?,?,?)").run(id,expectedVersion+1,to);
    db.exec("COMMIT");
  } catch (error) { db.exec("ROLLBACK"); throw error; }
}
try {
  transition("task-1",0,"running");
  db.close(); db = new DatabaseSync(path);
  assert.equal(db.prepare("SELECT state FROM tasks").get().state,"running");
  assert.throws(() => transition("task-1",0,"succeeded"),/STALE/);
  transition("task-1",1,"succeeded");
  assert.throws(() => transition("task-1",2,"failed"),/ILLEGAL/);
  const events = db.prepare("SELECT version,state FROM events ORDER BY version").all();
  assert.deepEqual(events.map(e => [e.version,e.state]),[[1,"running"],[2,"succeeded"]]);
  console.log("reopen: running; stale writer rejected; terminal protected");
  console.log("state and two versioned events committed together");
} finally { db.close(); rmSync(path); rmdirSync(dir); }
~~~

~~~text expect=S4-L01.mjs
reopen: running; stale writer rejected; terminal protected
state and two versioned events committed together
~~~

运行 npm run tutorial -- S4-L01。重新打开文件后依然 running，证明不是内存 Map。版本0的旧写者不能提交成功；版本2的终态不能改成失败。任务状态与事件在同一事务，避免“状态已经成功，但审计事件未写入”。

## 3. 把数据库版本接到前端

服务端返回 taskId、state、version。前端只应用同任务且更高版本的事件；重复版本忽略，版本跳跃时拉取快照校准。不要靠到达时间排序：旧事件可能因网络重试更晚到达。

前端“取消按钮已点击”可显示请求中，但最终取消状态来自服务端。取消与成功竞争时，由数据库允许的状态转换和条件更新决定胜者，再通知前端。不要让两个 Promise 的最后一次 setState 覆盖业务事实。

## 4. 恢复不等于继续重复执行

进程重启发现 running 时，需要判断租约是否过期、外部副作用结果是否可查询、attempt 是否有稳定幂等键。直接把所有 running 改回 queued 可能重复发送。S4-L02 用租约与 fencing token 处理旧工作者。

持久化还要考虑保留期限、敏感参数、事件体积、数据库备份与迁移。本例只有 id/state/version，没有保存用户原文或凭证；上线不要无选择地把全部 Prompt、工具结果存进 events。

## 故障练习与项目迁移

去掉版本条件，模拟取消后旧成功回调覆盖状态。把事件插入移出事务并主动抛错，观察状态和事件不一致。恢复后写一个自动核对脚本：每个任务最后事件版本必须等于快照版本。

项目练习：持久保存 task/run/attempt、停止原因和预算摘要，设计恢复规则并完成两次进程重启演示。提交状态图、非法转换测试、旧版本拒绝、事件原子性与 React 重放证据。本人解释数据库事实和 UI 乐观态的区别。

## 单页速记

- task 管目标，run 管编排，attempt 管尝试。
- 持久化保存事实，状态机约束可发生的变化。
- 条件版本更新拒绝旧写者，事务绑定状态与事件。
- 恢复前先判断副作用和租约，不能一律重跑。
