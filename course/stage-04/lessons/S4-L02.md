## 本课目标

- 先选交付语义
- 把重试限定在安全范围
- 理解租约不等于永不并发

## 1. 先选交付语义

队列把请求与执行解耦，但不能仅凭“用了队列”就声称恰好一次。确认丢失、worker 崩溃或可见性超时都可能使任务再次出现。对业务设计按可能重复交付处理，并把持久幂等结果与稳定意图键关联；不要把消息出队当成业务已完成。

## 2. 把重试限定在安全范围

临时故障可有次数和总期限受限的退避，并加入抖动避免同时冲击服务；参数非法、无权限等不可恢复错误不应机械重试。超过上限进入可观察的失败/死信路径。重试计划应持久化，重启之后不能把计数重新归零。

## 3. 理解租约不等于永不并发

worker 租约过期后，旧 worker 仍可能继续工作，新 worker 又获得任务。续租、取消和 fencing token 等机制需结合存储与下游是否检查版本设计。单纯给任务加 locked=true 没有到期恢复，也可能造成永久卡住。用故障注入测续租失败、重复消息与完成确认丢失。

## 实验：重复交付如何去重

先预测输出，再运行并修改一个条件。这是教学用的 JavaScript 机制演示，不是真实模型、数据库、协议 SDK 或生产系统。

~~~js
const processed = new Set();
let writes = 0;
for (const message of [{intent:"i-1"},{intent:"i-1"},{intent:"i-2"}]) {
  if (processed.has(message.intent)) {console.log("重复");continue;}
  processed.add(message.intent); writes++;
}
console.log({writes});
console.log("示例没有数据库原子性，也不证明故障恢复");
~~~

观察方向：三次交付对应两个不同意图；换进程或并发时还需持久原子机制。

提示：重复交付与重复业务意图不是同一个维度。
