# S4-L02 租约到期后，旧工作者不能继续交卷

## 先说我们要解决什么问题

W1领取任务后卡住。系统让W2接手，过了一会W1又恢复了。如果两边都能写“完成”，最后的状态就会乱。

## 先把概念讲清楚

队列把待做工作交给工作者（worker）。至少一次交付意味着可能重复收到，消费方必须处理重复。租约是有期限的领取资格，过期后可由别人接手。fencing token 是每次领取递增的代次编号，用来拒绝旧资格提交。

重试是一次新的执行尝试，不是把失败信息抹掉。暂时限流可以延后重试；参数错误应修正输入；写操作超时可能结果未知，先查回执，不能盲目再发。

## 名字与字段从哪里来

|名字或字段|来源与含义|
|---|---|
|now / until|课堂逻辑时间与租约截止时间；真实系统要统一时间裁决|
|token|本课递增代次，不是认证token|
|claim / commit|课堂领取、提交函数；真实项目需数据库原子条件|
|owner|工作者编号；单独使用它不能区分同一工作者的不同领取代次|

## 先读这个最小例子

网页“动手实验”运行相同代码。先找输入、检查与输出；assert 是课堂提供的检查函数，不是模型能力。

~~~js
let lease = { owner: null, until: 0, token: 0 };
function claim(owner, now) {
  if (now < lease.until) throw new Error("仍被占用");
  lease = { owner, until: now + 10, token: lease.token + 1 };
  return lease.token;
}
function commit(token, now) {
  return token === lease.token && now < lease.until;
}
const old = claim("W1", 0);
const latest = claim("W2", 11);
console.log("旧提交：", commit(old, 12), "新提交：", commit(latest, 12));
assert.equal(commit(old, 12), false);
~~~
## 运行结果与逐步解释

~~~text
旧提交： false 新提交： true
~~~

W1得到token1、到10过期；11时W2领取得到token2、到21过期。12时旧1与当前2不等，所以拒绝；新2仍在期限内，所以接受。这只控制本函数的提交，不会撤回W1已经发出的邮件。真实外部副作用仍需下游幂等支持或人工核对。

## 1. 一个崩溃恢复时间线

时刻0，W1 领取任务，租约到10。W1 停顿，时刻11，W2 重新领取。时刻12，W1 恢复并提交“完成”。如果只检查 state=running，W1 与 W2 都可能提交。

每次领取增加一个单调 token，提交必须携带自己领取时的 token。W2 拿到2后，W1 的1失效。这就是 fencing 思路。只保存 workerId 不够：同一个进程编号复用或同一工作者多次领取也需要区分世代。

## 代码阅读：租约像临时使用权，token 像世代编号

### 先区分时间与身份

lease_until 表示拥有权何时到期，owner 表示本次工作者，token 每次领取加1。currentTime 是测试注入的逻辑时间，不是真的让你等17秒。三者组合才能拒绝已经过期的执行者。

claimJob(workerId,currentTime) 用一条条件 UPDATE 同时检查可领取性并更新拥有者、期限、token 和 attempt。completeJob 只有 owner/token 匹配、租约未过期、状态仍运行中才成功。

### 按时间逐行推演

|时间|操作|为什么|
|---|---|---|
|0|W1领取，token=1|任务排队中|
|5|W2领不到|W1租约到10，尚未过期|
|11|W2领取，token=2|旧租约已过期|
|12|W1提交失败|token=1已陈旧|
|12|W2安排重试，next_at=17|当前拥有者允许重新排队|
|16|W3领不到|尚未到重试时间|
|17|W3领取，token=3|延迟满足|
|18|W3提交成功|拥有者、世代、期限都满足|

### 重试与重复执行不同

scheduleRetry 把同一业务任务再排队；attempt 增加，业务意图键不应随意更换。租约防止旧工作者提交数据库状态，却不能撤销它已经发出的外部邮件。外部副作用仍需要幂等或下游 fencing。

当前示例最多领取3次，但没有完整死信管理、续期和多机时钟处理；这些是后面的项目练习。不要把状态约束测试当成整个队列产品已完成。

### 带提示的练习

先去掉 token 条件，观察W1为何可能重新获得提交机会。再设计一个续期函数，条件应包含谁、哪一代、是否已过期。最后补“两连接竞争”和“下游发送已成功但响应丢失”，分别说明数据库与外部系统怎样恢复。

## 2. 用逻辑时钟复现

### 完整实操文件：S4-L02.mjs

~~~js file=S4-L02.mjs
// 使用题目注入的逻辑时间，逐步复现旧工作者与新工作者的竞争。
import assert from "node:assert/strict";
import { DatabaseSync } from "node:sqlite";
const database = new DatabaseSync(":memory:");
database.exec(
  `
CREATE TABLE jobs (
  id TEXT PRIMARY KEY,
  state TEXT,
  owner TEXT,
  lease_until INTEGER,
  token INTEGER,
  attempt INTEGER,
  next_at INTEGER
)
`,
);
database
  .prepare("INSERT INTO jobs VALUES(?,?,?,?,?,?,?)")
  .run("J1", "queued", null, 0, 0, 0, 0);
// 原子领取符合条件的任务，并返回这一轮独有的租约 token。
function claimJob(workerId, currentTime) {
  return database
    .prepare(
      `
UPDATE jobs
SET
  state = 'running',
  owner = ?,
  lease_until = ?,
  token = token + 1,
  attempt = attempt + 1
WHERE
  id = 'J1'
  AND attempt < 3
  AND (
    (
      state = 'queued'
      AND next_at <= ?
    )
    OR (
      state = 'running'
      AND lease_until <= ?
    )
  )
RETURNING
  token
`,
    )
    .get(workerId, currentTime + 10, currentTime, currentTime)?.token;
}
// 只有租约仍有效且 token/owner 都匹配，才允许提交成功。
function completeJob(workerId, leaseToken, currentTime) {
  return (
    database
      .prepare(
        `
UPDATE jobs
SET
  state = 'succeeded'
WHERE
  id = 'J1'
  AND state = 'running'
  AND owner = ?
  AND token = ?
  AND lease_until > ?
`,
      )
      .run(workerId, leaseToken, currentTime).changes === 1
  );
}
// 当前拥有者将任务重新排队，next_at 控制下一次可领取时间。
function scheduleRetry(workerId, leaseToken, currentTime) {
  return (
    database
      .prepare(
        `
UPDATE jobs
SET
  state = 'queued',
  next_at = ?,
  owner = NULL
WHERE
  id = 'J1'
  AND state = 'running'
  AND owner = ?
  AND token = ?
  AND lease_until > ?
`,
      )
      .run(currentTime + 5, workerId, leaseToken, currentTime).changes === 1
  );
}
try {
  const expiredLeaseToken = claimJob("W1", 0);
  assert.equal(expiredLeaseToken, 1);
  assert.equal(claimJob("W2", 5), undefined);
  const currentLeaseToken = claimJob("W2", 11);
  assert.equal(currentLeaseToken, 2);
  assert.equal(completeJob("W1", expiredLeaseToken, 12), false);
  assert.equal(scheduleRetry("W2", currentLeaseToken, 12), true);
  assert.equal(claimJob("W3", 16), undefined);
  const finalLeaseToken = claimJob("W3", 17);
  assert.equal(finalLeaseToken, 3);
  assert.equal(completeJob("W3", finalLeaseToken, 18), true);
  assert.equal(claimJob("W4", 100), undefined);
  assert.equal(database.prepare("SELECT attempt FROM jobs").get().attempt, 3);
  console.log("lease expiry -> token 2; stale token 1 rejected");
  console.log("retry delayed until 17; attempt 3 succeeded; terminal not reclaimed");
} finally {
  database.close();
}
~~~
~~~text expect=S4-L02.mjs
lease expiry -> token 2; stale token 1 rejected
retry delayed until 17; attempt 3 succeeded; terminal not reclaimed
~~~

**选做本地验证：**运行 npm run tutorial -- S4-L02。领取是单条条件 UPDATE，避免“先查再改”的竞争窗口。数据库在该语句的写入边界上裁决；本实验顺序安排逻辑竞争，并没有覆盖多连接锁等待、数据库宕机或时钟漂移。

## 3. 租约仍有外部边界

如果 W1 在检查 token 后发邮件，而 W2 也发邮件，数据库拒绝 W1 最终状态不能撤回邮件。下游写入也必须支持 fencing 或幂等意图键。每层都写清楚“拒绝旧结果”与“拒绝旧副作用”是否真的做到。

租约需要心跳续期；续期条件仍包含 token、owner 和当前有效租约。续期失败应停止工作，不能继续假定自己拥有任务。跨机器最好使用数据库时间作为统一裁决；逻辑时钟只是可重复测试工具。

## 4. 什么错误值得重试

短暂限流、连接中断可能重试；参数非法、无权限、确定业务不存在通常不应盲重试。写操作超时可能是结果未知，先查幂等状态。退避可使用有上限的指数延迟与随机抖动，但抖动必须能在测试中固定随机源。

重试消耗 attempt、时间与费用预算。达到最大次数后转入明确失败或待人工处理，保留最后错误与恢复入口。死信不是把问题藏起来的文件夹，要有可查询、分派与受控重放规则。

## 单页速记

- 队列重复投递是需要处理的正常情况。

- 旧工作者的状态与副作用要分别防护。
