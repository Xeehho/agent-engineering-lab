# S4-L04 先查再改，为什么可能覆盖别人

## 先说我们要解决什么问题

两个工作者都读到任务version=1，然后分别保存修改。如果后保存的一方不检查版本，就会覆盖先保存的结果。

## 先把概念讲清楚

SQL是操作关系数据库的语言，表是一组按列约定的记录。索引为特定查询维护查找结构，会占空间并增加写入成本；不是越多越好。事务把一组数据库操作作为一个提交单元，具体隔离级别决定并发可见性与冲突行为。

乐观并发控制是保存时检查“我读到的版本仍然是当前版本吗”。SQL可把检查与更新写进同一语句：UPDATE tasks SET version=version+1 ... WHERE id=? AND version=?，再检查实际改了几行。

## 名字与字段从哪里来

|名字或字段|来源与含义|
|---|---|
|row / version|课堂模拟一行记录与修改版本|
|expectedVersion|调用方读到的旧版本，不能直接当当前版本|
|save|课堂原子步骤的顺序模拟；不是数据库事务|
|updated rows / UNIQUE|SQL返回的修改行数概念与唯一约束；真实语法看选用数据库|

## 先读这个最小例子

网页“动手实验”运行相同代码。先找输入、检查与输出；assert 是课堂提供的检查函数，不是模型能力。

~~~js
let row = { id: "task-42", version: 1, state: "running" };
function save(expectedVersion, next) {
  if (row.version !== expectedVersion) return false;
  row = { ...row, state: next, version: row.version + 1 };
  return true;
}
const a = save(1, "succeeded");
const b = save(1, "failed");
console.log("A保存：", a, "B保存：", b, row.state);
assert.equal(row.state, "succeeded");
~~~
## 运行结果与逐步解释

~~~text
A保存： true B保存： false succeeded
~~~

A保存时版本仍为1，成功后变2；B带着旧1来保存时不匹配，所以不覆盖。浏览器顺序演示没有验证数据库锁和实际并发。进阶使用真实SQLite条件更新与事务，再考虑PostgreSQL等数据库的隔离差异。数据库事务也不能自动覆盖外部邮件API。

## 1. 从查询需求反推数据模型

需求是“查看当前租户最近的运行中任务”。至少需要 tenant、state、created_at、id，并且分页必须稳定。只按时间排序，时间相同时翻页可能重复或遗漏，所以加 id 作为确定性次序。

关系表适合可查询的任务、尝试、事件、审批、版本；大原文与模型输出可存对象存储，再保存受控引用。把所有字段塞进一个 JSON，初期灵活，却容易失去约束、索引和清晰迁移路径。

## 代码阅读：把一条查询读成过滤、排序和上限

### 先翻译 SQL

任务列表只要当前租户、运行中任务，按创建时间倒序，时间相同时再按id倒序，最多5条。WHERE 决定范围，ORDER BY 决定顺序，LIMIT 决定数量。SELECT 只取id，避免无用字段。

索引 idx_task_feed 按 tenant、state、created_at、id 排列。前两个服务等值过滤，后两个服务排序。这是为具体查询设计的索引，不是“任何查询都会更快”的开关。

### 按三个阶段运行

|阶段|观察点|能说明什么|
|---|---|---|
|未建索引|EXPLAIN QUERY PLAN|原来的访问路径|
|建立索引后|计划包含idx_task_feed|规划器使用该索引|
|执行查询|997、995、991、989、985|当前夹具排序和过滤正确|

任务号既要是A租户的奇数，又不能是已完成的3的倍数，所以999被排除。你应能手算前几条，再运行验证，而不是只相信输出。

### 回滚验证什么

事务先将997改成done，再插入引用不存在任务的事件。开启外键后，插入失败；ROLLBACK 恢复前面的状态。这个例子说明多步写入如何保持一致，不能推出所有数据库配置与隔离级别都相同。

参数化把 A' OR 1=1 这样的输入当普通值。它找不到租户就返回空列表；应用仍必须另做授权，参数化不会自动补上 tenant 条件。

### 带提示的练习

先删索引观察计划，再恢复。构造两个相同时间的任务，解释为什么排序还需要id。最后设计下一页游标，保留租户和状态过滤，别只把“上一条id”拼到任意查询里。

## 2. 实际比较查询计划

### 完整实操文件：S4-L04.mjs

~~~js file=S4-L04.mjs
// 先观察查询计划，再加索引；用失败事务观察状态是否回滚。
import assert from "node:assert/strict";
import { DatabaseSync } from "node:sqlite";
const database = new DatabaseSync(":memory:");
try {
  database.exec(
    `
PRAGMA foreign_keys = ON;

CREATE TABLE tasks (
  id INTEGER PRIMARY KEY,
  tenant TEXT NOT NULL,
  state TEXT NOT NULL,
  created_at INTEGER NOT NULL
);

CREATE TABLE events (
  task_id INTEGER REFERENCES tasks (id),
  version INTEGER,
  UNIQUE (task_id, version)
)
`,
  );
  const insertTask = database.prepare("INSERT INTO tasks VALUES(?,?,?,?)");
  database.exec("BEGIN");
  for (let taskNumber = 1; taskNumber <= 1000; taskNumber++) {
    insertTask.run(
      taskNumber,
      taskNumber % 2 ? "A" : "B",
      taskNumber % 3 ? "running" : "done",
      taskNumber,
    );
  }
  database.exec("COMMIT");
  const taskFeedQuery = `
SELECT
  id
FROM
  tasks
WHERE
  tenant = ?
  AND state = ?
ORDER BY
  created_at DESC,
  id DESC
LIMIT
  5
`;
  const readQueryPlan = () =>
    database
      .prepare("EXPLAIN QUERY PLAN " + taskFeedQuery)
      .all("A", "running")
      .map((r) => r.detail)
      .join(" | ");
  const planBeforeIndex = readQueryPlan();
  database.exec(
    "CREATE INDEX idx_task_feed ON tasks(tenant,state,created_at DESC,id DESC)",
  );
  const planAfterIndex = readQueryPlan();
  assert.ok(!planBeforeIndex.includes("idx_task_feed"));
  assert.ok(planAfterIndex.includes("idx_task_feed"));
  const recentTaskIds = database
    .prepare(taskFeedQuery)
    .all("A", "running")
    .map((r) => r.id);
  assert.deepEqual(recentTaskIds, [997, 995, 991, 989, 985]);
  const previousTaskState = database
    .prepare("SELECT state FROM tasks WHERE id=997")
    .get().state;
  database.exec("BEGIN");
  try {
    database.prepare("UPDATE tasks SET state='done' WHERE id=997").run();
    database.prepare("INSERT INTO events VALUES(?,?)").run(999999, 1);
    database.exec("COMMIT");
  } catch {
    database.exec("ROLLBACK");
  }
  assert.equal(
    database.prepare("SELECT state FROM tasks WHERE id=997").get().state,
    previousTaskState,
  );
  assert.equal(
    database.prepare("SELECT id FROM tasks WHERE tenant=?").all("A' OR 1=1 --").length,
    0,
  );
  console.log("query plan uses idx_task_feed; stable top IDs=997,995,991,989,985");
  console.log("foreign-key failure rolled back state; SQL-looking value stayed data");
} finally {
  database.close();
}
~~~
~~~text expect=S4-L04.mjs
query plan uses idx_task_feed; stable top IDs=997,995,991,989,985
foreign-key failure rolled back state; SQL-looking value stayed data
~~~

## 3. 阅读复合索引

tenant 与 state 对应等值过滤，后面的 created_at 与 id 对应排序。这个索引服务这条查询，不意味着所有查询都快。只按 state 查、全文模糊搜索或不同排序，可能需要不同计划。索引也会增加写入成本与磁盘占用。

下一页可以用最后一条的 created_at 与 id 作为游标，条件是时间更小，或时间相同且 id 更小，同时保留 tenant/state。大偏移量 OFFSET 可能扫描许多不用的行；数据在翻页时变化也可能带来重复。游标还要绑定查询条件，不能跨租户随意复用。

## 4. 事务与约束共同维护事实

实验先更新任务，再插入引用不存在任务的事件。foreign_keys 打开后插入失败，ROLLBACK 使前面的状态恢复。若忽略错误仍提交，就会留下不一致。

应用层检查提高错误信息质量；数据库 NOT NULL、UNIQUE、外键等约束裁决并发写入下的底线。不同数据库默认行为不同，SQLite 的外键开关要明确设置，不能把开发环境偶然工作当作迁移后的保证。

参数化值把看起来像 SQL 的字符串当数据。列名、排序方向等动态语法通常不能靠值占位符代入，需要服务器允许列表。参数化也不替代租户过滤和字段授权。

## 5. 迁移要可回退

增加非空字段时，旧记录可能没有值。可先增可空列或合理默认值，分批回填，再加约束；在线索引与锁行为按所用数据库核对。应用新旧版本在部署窗口可能共存，接口和表结构应考虑兼容，而非要求所有进程瞬间切换。

备份恢复要实际演练，不能以“有备份文件”当恢复成功。记录数据库版本、迁移版本、恢复点和丢失窗口。
