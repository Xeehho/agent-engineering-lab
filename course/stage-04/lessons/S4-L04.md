# S4-L04 SQL、索引与事务：让系统可查询

AI 应用工程师需要能解释数据怎么存、为什么慢、并发时谁胜出。本课使用实际 SQLite SQL、查询计划与回滚；它不替代 PostgreSQL 生产性能测试，不代表学习者已掌握。

## 1. 从查询需求反推数据模型

需求是“查看当前租户最近的运行中任务”。至少需要 tenant、state、created_at、id，并且分页必须稳定。只按时间排序，时间相同时翻页可能重复或遗漏，所以加 id 作为确定性次序。

关系表适合可查询的任务、尝试、事件、审批、版本；大原文与模型输出可存对象存储，再保存受控引用。把所有字段塞进一个 JSON，初期灵活，却容易失去约束、索引和清晰迁移路径。

## 2. 实际比较查询计划

~~~js file=S4-L04.mjs
import assert from "node:assert/strict";
import { DatabaseSync } from "node:sqlite";
const db = new DatabaseSync(":memory:");
try {
  db.exec("PRAGMA foreign_keys=ON; CREATE TABLE tasks(id INTEGER PRIMARY KEY,tenant TEXT NOT NULL,state TEXT NOT NULL,created_at INTEGER NOT NULL); CREATE TABLE events(task_id INTEGER REFERENCES tasks(id),version INTEGER,UNIQUE(task_id,version))");
  const insert = db.prepare("INSERT INTO tasks VALUES(?,?,?,?)");
  db.exec("BEGIN");
  for (let i=1;i<=1000;i++) insert.run(i,i%2?"A":"B",i%3?"running":"done",i);
  db.exec("COMMIT");
  const sql = "SELECT id FROM tasks WHERE tenant=? AND state=? ORDER BY created_at DESC,id DESC LIMIT 5";
  const plan = () => db.prepare("EXPLAIN QUERY PLAN "+sql).all("A","running").map(r => r.detail).join(" | ");
  const before = plan();
  db.exec("CREATE INDEX idx_task_feed ON tasks(tenant,state,created_at DESC,id DESC)");
  const after = plan();
  assert.ok(!before.includes("idx_task_feed"));
  assert.ok(after.includes("idx_task_feed"));
  const ids = db.prepare(sql).all("A","running").map(r => r.id);
  assert.deepEqual(ids,[997,995,991,989,985]);
  const prior = db.prepare("SELECT state FROM tasks WHERE id=997").get().state;
  db.exec("BEGIN");
  try {
    db.prepare("UPDATE tasks SET state='done' WHERE id=997").run();
    db.prepare("INSERT INTO events VALUES(?,?)").run(999999,1);
    db.exec("COMMIT");
  } catch {
    db.exec("ROLLBACK");
  }
  assert.equal(db.prepare("SELECT state FROM tasks WHERE id=997").get().state,prior);
  assert.equal(db.prepare("SELECT id FROM tasks WHERE tenant=?").all("A' OR 1=1 --").length,0);
  console.log("query plan uses idx_task_feed; stable top IDs=997,995,991,989,985");
  console.log("foreign-key failure rolled back state; SQL-looking value stayed data");
} finally { db.close(); }
~~~

foreign-key failure rolled back state; SQL-looking value stayed data
~~~

运行 npm run tutorial -- S4-L04。这里验证查询计划选择了索引，没有用一次毫秒差证明“快了100倍”。缓存、样本量和硬件都会影响时间；性能结论需要代表性数据、重复测量与查询计划共同支持。

## 3. 阅读复合索引

tenant 与 state 对应等值过滤，后面的 created_at 与 id 对应排序。这个索引服务这条查询，不意味着所有查询都快。只按 state 查、全文模糊搜索或不同排序，可能需要不同计划。索引也会增加写入成本与磁盘占用。

下一页可以用最后一条的 created_at 与 id 作为游标，条件是时间更小，或时间相同且 id 更小，同时保留 tenant/state。大偏移量 OFFSET 可能扫描许多不用的行；数据在翻页时变化也可能带来重复。游标还要绑定查询条件，不能跨租户随意复用。

## 4. 事务与约束共同维护事实

实验先更新任务，再插入引用不存在任务的事件。foreign_keys 打开后插入失败，ROLLBACK 使前面的状态恢复。若忽略错误仍提交，就会留下不一致。

应用层检查提高错误信息质量；数据库 NOT NULL、UNIQUE、外键等约束裁决并发写入下的底线。不同数据库默认行为不同，SQLite 的外键开关要明确设置，不能把开发环境偶然工作当作迁移后的保证。

参数化值把看起来像 SQL 的字符串当数据。列名、排序方向等动态语法通常不能靠值占位符代入，需要服务器允许列表。参数化也不替代租户过滤和字段授权。

## 5. 迁移要可回退

增加非空字段时，旧记录可能没有值。可先增可空列或合理默认值，分批回填，再加约束；在线索引与锁行为按所用数据库核对。应用新旧版本在部署窗口可能共存，接口和表结构应考虑兼容，而非要求所有进程瞬间切换。

备份恢复要实际演练，不能以“有备份文件”当恢复成功。记录数据库版本、迁移版本、恢复点和丢失窗口。

## 故障练习与项目迁移

删除索引比较计划；去掉排序的 id，构造同时间记录与分页测试；关闭 foreign_keys，观察约束失效。每个实验恢复后重新验证。

项目练习：为任务列表、尝试查询和事件回放设计三条 SQL，给出代表性数据、索引与计划。加一次故障回滚和迁移演练，解释读写代价。不要把这份1000行的本地实验写成生产容量报告。

## 单页速记

- 先明确过滤、排序和分页，再设计表与索引。
- 查询计划解释访问路径，单次耗时不能承担全部性能结论。
- 约束与事务维护一致性，参数化与授权分别负责不同边界。
- 迁移、备份与恢复需要真实演练。
