# S6-L02 Handoff、证据与冲突裁决

**网页主线：直接阅读讲解 → 动手实验 → 随堂练习 → 公开自测 → 复习速记。无需启动项目、安装依赖或提供 API Key。**

本课网页任务：给相同事实返回不同值，或额外添加 approved 字段。

网页实验范围：手动结构/版本/证据验证，不把同源赞同当独立事实。

**选做实操说明：**下面涉及 Node、Python、数据库或 SDK 的环境、命令和完整文件供进阶使用，不是阅读本课的前置条件。


多角色系统最容易丢失的不是文本，而是来源、状态与责任。本课验证结构化交接和冲突停止，所有结论是固定夹具，没有模型生成，不代表学习者已掌握。

## 1. 为什么不能把上一段聊天直接交给下一个角色

检索者说“看起来可能是新版规则”，摘要者写成“新版规定如此”，执行者又当作已批准动作。一次压缩把不确定性、来源和权限都丢失了。

交接至少应有 taskId、输入版本、产物类型、claims、证据引用、未解决事项、状态与下一步建议。建议不等于批准，子角色也不能把自己的预算、权限或“已验证”声明直接升级为控制面事实。

## 代码阅读：交接的是可核查产物

### 先看一份 handoff

taskId对应目标，inputVersion对应这次依据的输入快照，status表示能否继续，claims列出事实与证据，unresolved保留未解决事项。它不是任意一段聊天，也不能夹带approved=true授予执行权限。

validateHandoff 先用Zod检查形状，再核对任务和版本，最后检查每个证据是否存在、当前且属于允许租户。reconcile只负责合并已接收产物，不替代来源的语义支持核查。

### 用同一事实看四条路径

|交接内容|结果|原因|
|---|---|---|
|两份都说reviewDays=2|ready|字段一致|
|一份2、一份3|blocked|同一事实值冲突|
|inputVersion=1，当前为2|拒绝|旧输入产物|
|引用B的私有证据|拒绝|来源不在授权范围|

即使两份都说2，也可能共同依赖同一错误来源。代码只证明一致，不证明独立正确。

### 检查结构与检查事实分开

evidenceIds中存在rule-v2，不代表value一定受它支持。把value改成3仍可能通过来源检查，之后才由冲突、规则或语义评分发现。正确设计应保存每条claim的具体引文与限制条件，沿S5的方法复核。

### 带提示的练习

先构造“审核两天”和“到账三天”，说明它们是否真的冲突；必要时拆分不同事实key。再模拟取消后迟到的交接，接收端要同时检查当前任务状态与版本。未知变式中，先问缺什么证据，不急着用多数票裁决。

## 2. 用 Schema 与证据注册表验证

### 完整实操文件：S6-L02.mjs

~~~js file=S6-L02.mjs
// 交接先验证形状和证据范围，再检查未决事项与冲突。
import assert from "node:assert/strict";
import { z } from "zod";
const handoffSchema = z
  .object({
    taskId: z.string(),
    inputVersion: z.number().int(),
    status: z.enum(["ready", "blocked"]),
    claims: z.array(
      z
        .object({
          key: z.string(),
          value: z.string(),
          evidenceIds: z.array(z.string()).min(1),
        })
        .strict(),
    ),
    unresolved: z.array(z.string()),
  })
  .strict();
const evidence = new Map([
  ["rule-v2", { current: true, tenant: "A", text: "退款审核需两天" }],
  ["rule-v1", { current: false, tenant: "A", text: "旧版需一天" }],
  ["private-B", { current: true, tenant: "B", text: "B 的规则" }],
]);
// 对齐任务、输入版本和来源权限，但不宣称已验证语义支持。
function validateHandoff(rawHandoff, context) {
  const handoff = handoffSchema.parse(rawHandoff);
  if (handoff.taskId !== context.taskId || handoff.inputVersion !== context.version) {
    throw new Error("STALE_HANDOFF");
  }
  for (const claim of handoff.claims) {
    for (const evidenceId of claim.evidenceIds) {
      const sourceEvidence = evidence.get(evidenceId);
      if (
        !sourceEvidence ||
        !sourceEvidence.current ||
        sourceEvidence.tenant !== context.tenant
      ) {
        throw new Error("INVALID_EVIDENCE");
      }
    }
  }
  return handoff;
}
// 相同事实可以合并，冲突或未决事项必须阻止继续。
function reconcile(handoffs) {
  const factValues = new Map();
  for (const handoff of handoffs) {
    if (handoff.status === "blocked" || handoff.unresolved.length) {
      return { status: "blocked", reason: "UNRESOLVED" };
    }
    for (const claim of handoff.claims) {
      if (factValues.has(claim.key) && factValues.get(claim.key) !== claim.value) {
        return { status: "blocked", reason: "CONFLICT", key: claim.key };
      }
      factValues.set(claim.key, claim.value);
    }
  }
  return { status: "ready", facts: Object.fromEntries(factValues) };
}
const fixtureHandoff = {
  taskId: "T",
  inputVersion: 2,
  status: "ready",
  claims: [{ key: "reviewDays", value: "2", evidenceIds: ["rule-v2"] }],
  unresolved: [],
};
const expectedContext = { taskId: "T", version: 2, tenant: "A" };
const acceptedHandoff = validateHandoff(fixtureHandoff, expectedContext);
assert.equal(reconcile([acceptedHandoff, acceptedHandoff]).status, "ready");
const conflictingHandoff = validateHandoff(
  {
    ...fixtureHandoff,
    claims: [{ key: "reviewDays", value: "3", evidenceIds: ["rule-v2"] }],
  },
  expectedContext,
);
assert.deepEqual(reconcile([acceptedHandoff, conflictingHandoff]), {
  status: "blocked",
  reason: "CONFLICT",
  key: "reviewDays",
});
assert.throws(
  () => validateHandoff({ ...fixtureHandoff, inputVersion: 1 }, expectedContext),
  /STALE/,
);
assert.throws(
  () =>
    validateHandoff(
      {
        ...fixtureHandoff,
        claims: [{ key: "x", value: "x", evidenceIds: ["private-B"] }],
      },
      expectedContext,
    ),
  /EVIDENCE/,
);
assert.throws(() =>
  validateHandoff({ ...fixtureHandoff, approved: true }, expectedContext),
);
console.log("handoff schema/version/evidence scope: passed");
console.log("conflict blocked; same-source agreement not treated as independent proof");
~~~

conflict blocked; same-source agreement not treated as independent proof
~~~

**选做本地验证：**运行 npm run tutorial -- S6-L02。Schema 拒绝额外 approved 字段，避免角色用产物夹带控制信息。有效 evidenceId 只证明来源在授权注册表中；value=3 仍能引用“需两天”，所以语义核查要沿用 S5-L03 的支持度验证。

## 3. 冲突不能靠多数票随便消除

三个角色读取同一错误摘要后都说“一天”，不是三份独立证据。先按证据来源、版本、权威规则和具体条件查冲突。数量投票只在明确设计并验证的前提下使用，不能取代事实核验。

如果一份说“审核两天”，另一份说“到账三天”，它们可能讨论不同概念。结构化 key 的业务定义能减少伪冲突；真正冲突无法裁决时，应暂停、补查或人工处理，而不是让最后一个角色强行整合。

## 4. 交接的执行语义

handoff 是传递产物与后续处理权，不是自动复制全部历史、权限与凭证。目标角色只收到所需最小上下文。敏感原文通过受控引用读取，日志保存关联 ID。

重复交接用产物 ID 与版本去重；接收端记录已接受版本，迟到产物不覆盖新版本。任务取消后，仍可能收到子任务结果，接收端需要检查当前任务状态。角色失败与业务 blocked 分开记录，前者可能重试，后者可能需要补信息。

## 故障练习与项目迁移

构造引用真实但值错误、两个角色同源一致、不同概念同 key、旧版本晚到四种案例。逐个指出 Schema、权限、版本和语义检查各能拦住什么。

项目练习：为检索→草稿→审阅设计交接契约，保存产物版本、证据、未决事项和停止原因。提交冲突升级与取消后迟到结果的拒绝证据，不能用角色聊天截图代替数据流解释。

## 单页速记

- 交接保留任务版本、证据、不确定性和未决事项。
- 产物数据不能夹带权限与批准。
- 同源多数不是独立事实验证。
- 冲突先查概念与来源，不能裁决时明确停止。
