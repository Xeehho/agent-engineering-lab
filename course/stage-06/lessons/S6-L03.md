# S6-L03 同一批任务，连失败成本一起比较

## 先说我们要解决什么问题

协作方案成功的例子很漂亮，但失败时重试很多次。如果只展示成功截图，就看不出它是否值得投入。

## 先把概念讲清楚

比较方案必须用同一数据集、同样验收口径和预算。质量、延迟和成本要一起看；失败请求消耗的费用与时间也计入。端到端延迟是用户等待总时间，并行任务不能直接把各分支耗时相加当等待时间。

先用几条固定记录学会分母，再扩大真实样本。平均数之外还要看分层错误和长尾，例如p95表示95%的观察值不超过该位置的延迟，少量样本的分位数很不稳定。

## 名字与字段从哪里来

|名字或字段|来源与含义|
|---|---|
|runs / ok / cost|课堂运行记录、是否验收通过、合成成本单位|
|successRate / totalCost|课堂汇总指标，不是服务商账单字段|
|costPerSuccess|总尝试成本除以成功数；无成功时需明确无定义|
|reduce|JavaScript聚合方法，失败记录不能先过滤掉|

## 先读这个最小例子

网页“动手实验”运行相同代码。先找输入、检查与输出；assert 是课堂提供的检查函数，不是模型能力。

~~~js
const runs = [
  { ok: true, cost: 2 },
  { ok: false, cost: 5 },
  { ok: true, cost: 2 },
];
const successes = runs.filter((run) => run.ok).length;
const totalCost = runs.reduce((sum, run) => sum + run.cost, 0);
console.log("成功：", successes + "/" + runs.length);
console.log("总成本：", totalCost, "每次成功成本：", totalCost / successes);
assert.equal(totalCost, 9);
~~~
## 运行结果与逐步解释

~~~text
成功： 2/3
总成本： 9 每次成功成本： 4.5
~~~

两次成功、一次失败，总成本2+5+2=9。除以两次成功得到4.5，失败的5没有消失。这是合成算术，不代表任何真实模型价格或方案效果。真实结论还需单Agent/Workflow/多Agent同集重复运行、记录变更并分析不确定性。

## 1. 冻结比较条件

对照应使用同一任务集、输入版本、工具数据、评分规则和可比较的模型配置。先记录单流程基线，再引入一个变化，例如增加审阅者。若同时换模型、提示、检索与角色，无法归因。

质量包括任务成功、关键错误、拒答与引用支持；成本包括所有角色、失败、重试与工具；延迟包括用户实际等待时间。只计算成功请求的费用与延迟，会把失败代价藏起来。

## 代码阅读：总分相同可能藏着退步

### 三个函数各做一件事

paired按任务ID对齐两个方案，列出原来失败现在成功的wins与原来成功现在失败的losses。summary计算成功数、总费用、每成功任务成本和延迟。quantile采用nearest-rank：排序后取向上取整的排名。

|任务|基线|候选|配对结论|
|---|---|---|---|
|a|成功|成功|持平|
|b|失败|成功|胜出|
|c|成功|失败|退步|
|d|成功|成功|持平|

两个方案都是3/4，但失败对象变了。如果c是关键企业场景，不能凭平均分相同就随意替换。

### 手算成本与延迟

基线总费用8，候选17；每成功任务成本分别为8/3与17/3，失败费用不能删除。四条样本按nearest-rank取p95，实际取最大值，所以是150与180；这不代表线上尾延迟已经可靠估计。

两个并行读取分别耗时40与60，随后生成耗时30。墙钟近似max(40,60)+30=90，总工作量40+60+30=130。模型和工具费用要累加，用户等待时间则沿实际关键路径观察。

### 带提示的练习

先删除一个失败任务，观察配对检查为什么应拒绝。再只统计成功请求费用，指出分母选择造成的偏差。做真实对照时，固定样本、模型和工具数据，只改变一个主要因素，并保留逐条输出与回归案例。

## 2. 计算配对结果

### 完整实操文件：S6-L03.mjs

~~~js file=S6-L03.mjs
import assert from "node:assert/strict";

// 所有费用和耗时均为合成单位，完整保留失败任务。
const baselineRuns = [
  { id: "a", ok: true, cost: 2, latency: 100 },
  { id: "b", ok: false, cost: 2, latency: 150 },
  { id: "c", ok: true, cost: 2, latency: 120 },
  { id: "d", ok: true, cost: 2, latency: 130 },
];
const candidateRuns = [
  { id: "a", ok: true, cost: 4, latency: 160 },
  { id: "b", ok: true, cost: 5, latency: 180 },
  { id: "c", ok: false, cost: 4, latency: 170 },
  { id: "d", ok: true, cost: 4, latency: 150 },
];

function quantile(values, probability) {
  if (values.length === 0) {
    return null;
  }
  if (!(probability > 0 && probability <= 1)) {
    throw new Error("INVALID_QUANTILE");
  }
  const sortedValues = [...values].sort((left, right) => left - right);
  const rank = Math.ceil(probability * sortedValues.length);
  return sortedValues[rank - 1];
}

function summary(runs) {
  const successCount = runs.filter((run) => run.ok).length;
  const totalCost = runs.reduce((sum, run) => sum + run.cost, 0);
  return {
    successes: successCount,
    n: runs.length,
    total: totalCost,
    costPerSuccess: successCount === 0 ? null : totalCost / successCount,
    p95: quantile(
      runs.map((run) => run.latency),
      0.95,
    ),
  };
}

function paired(baseline, candidate) {
  const candidateById = new Map(candidate.map((run) => [run.id, run]));
  const uniqueBaselineIds = new Set(baseline.map((run) => run.id));
  if (
    candidateById.size !== candidate.length ||
    uniqueBaselineIds.size !== baseline.length ||
    baseline.length !== candidate.length
  ) {
    throw new Error("UNPAIRED");
  }

  const wins = [];
  const losses = [];
  for (const baselineRun of baseline) {
    const candidateRun = candidateById.get(baselineRun.id);
    if (!candidateRun) {
      throw new Error("UNPAIRED");
    }
    if (!baselineRun.ok && candidateRun.ok) {
      wins.push(baselineRun.id);
    }
    if (baselineRun.ok && !candidateRun.ok) {
      losses.push(baselineRun.id);
    }
  }
  return { wins, losses };
}

assert.deepEqual(paired(baselineRuns, candidateRuns), { wins: ["b"], losses: ["c"] });
const baselineSummary = summary(baselineRuns);
const candidateSummary = summary(candidateRuns);
assert.equal(baselineSummary.successes, candidateSummary.successes);
assert.equal(baselineSummary.total, 8);
assert.equal(candidateSummary.total, 17);
assert.equal(baselineSummary.p95, 150);
assert.equal(candidateSummary.p95, 180);
assert.equal(candidateSummary.costPerSuccess, 17 / 3);
assert.throws(() => paired(baselineRuns, candidateRuns.slice(1)), /UNPAIRED/);
assert.equal(summary([]).costPerSuccess, null);

const parallelWallTime = Math.max(40, 60) + 30;
const totalWorkTime = 40 + 60 + 30;
assert.equal(parallelWallTime, 90);
assert.equal(totalWorkTime, 130);
console.log("both success=3/4; candidate wins=b, regressions=c; cost=8 -> 17");
console.log("nearest-rank p95=150 -> 180; parallel wall=90 vs total work=130");
~~~
~~~text expect=S6-L03.mjs
both success=3/4; candidate wins=b, regressions=c; cost=8 -> 17
nearest-rank p95=150 -> 180; parallel wall=90 vs total work=130
~~~

**选做本地验证：**运行 npm run tutorial -- S6-L03。总成功数相同却换了失败任务，说明只看平均分会隐藏退步。费用分母是成功数，但分子包含失败费用。四条样本的 p95 就是最大值，不能据此预测线上尾延迟；本课明确使用 nearest-rank 定义，不混用插值算法。

## 3. 什么时候值得增加角色

如果关键缺陷明显减少、覆盖任务增加，且成本与延迟落在预算内，多角色可能值得。如果只是答案变长、角色互夸，或总分相同却费用翻倍，应保留简单方案。不同任务可以路由到不同复杂度，不必所有请求都走最贵路径。

统计上，模型随机性、样本相关性与评分误差会影响结论。保存逐条重复运行，给不确定性估计；不要在四条合成数据上编造显著性。用于阈值选择的样本不能再当独立最终证据。

## 4. 公平记录失败与取消

超时请求计入延迟与失败，取消后仍发生的上游消耗也计入成本。并行角色的 token 与费用应相加，但墙钟时长按实际 trace 计算。工具缓存命中、重试和限流都会影响对照，需记录条件或在固定实验中控制。

成本来自服务计量、采用价格与计费单位；本例 cost 只是合成单位。真实账单还可能包含缓存、不同输入输出价格和其他服务费用，报告注明哪些已覆盖。

## 故障练习与项目迁移

只保留成功请求重新计算，解释偏差。移除 c 的回归，观察“漂亮总分”如何出现。把并行工作相加当响应时间，画关键路径指出错误。

项目练习：对确定性流程、单 Agent 与一个有依据的多角色方案运行同一组任务，发布逐条结果、胜负、关键失败、全费用与延迟分布。最终架构选择写清适用任务和预算，不以角色数量作为能力证明。

## 单页速记

- 一次改变一个主要因素，同集配对比较。
- 平均数之外必须看回归、关键失败与分母。
- 成本包含失败，延迟区分墙钟与总工作量。
- 小样本如实报告不确定性，复杂度由收益证明。
