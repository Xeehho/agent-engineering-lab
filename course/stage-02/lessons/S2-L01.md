## 本课目标

- 把服务商协议隔离在适配器

## 1. 拆开提议、校验、授权与执行

用户要查工单 T-42，模型可能输出工具名称和参数。这个输出是一项行动提议，不是已经执行的事实。应用负责解析参数、选择允许的工具、校验数据、结合当前身份授权，执行后再把真实结果关联回工具调用。模型不应能随意指定服务器函数名、SQL 或系统命令。

## 2. 设计窄而清晰的工具契约

先提供 getTicket({ticketId})、searchDocs({query,limit}) 这样的有限能力，明确每个字段的含义、范围、缺失时行为以及返回上限。返回内容要含来源与错误类别，而不是只给“成功”。同名工具随版本改变返回结构，会破坏后续决策，所以工具契约也需要版本与回归样例。

## 3. 把服务商协议隔离在适配器

不同模型 API 对工具调用标识、参数文本和结果消息的格式可能不同。内部统一成 callId/name/arguments，再由适配器映射；不能把一家 SDK 的字段当作通用协议。演示只模拟分发，不访问真实服务，更不能证明真实模型一定会选对工具。

## 实验：工具名存在，就能调用吗？

先预测输出，再运行并修改一个条件。这是教学用的 JavaScript 机制演示，不是真实模型、数据库、协议 SDK 或生产系统。

~~~js
const allowed = new Map([["getTicket", args => ({id:args.ticketId,status:"open"})]]);
for (const call of [{name:"getTicket",args:{ticketId:"T-42"}},{name:"deleteDatabase",args:{}}]) {
  const handler = allowed.get(call.name);
  console.log(handler ? handler(call.args) : {error:"UNKNOWN_TOOL"});
}
~~~

观察方向：未知工具被拒绝；把合法工具参数改为空，再指出演示还缺什么校验。

提示：这个分发器还不是完整授权器。
