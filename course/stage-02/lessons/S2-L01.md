## 本课目标

- 实现提议、解析、授权、执行、结果关联的完整小路径。
- 通过未知工具、非法参数与越权案例理解执行边界。
- 把服务商消息格式与内部业务契约分开。

## 1. 模型为什么不能直接调用你的函数

模型返回 getTicket({ticketId:"T-42"}) 时，本质上给出了名称和参数。它没有获得服务器函数指针，也没有因为写出 tenantId 就自动变成那个租户的用户。应用必须决定这个操作是否存在、参数是否可接收、当前身份是否有权执行。

五步路径是：向模型描述可用工具；收到工具提议；应用校验并执行；把真实结果关联回 callId；模型继续或生成最终回答。不同服务的消息字段不同，但应用的责任不会消失。

## 代码阅读：模型的一个提议经过哪些门

### 先读两种数据

validProposal 是模型提议的夹具：id 关联本次调用，name 选择工具，arguments 是 JSON 文本。authenticatedContext 是应用提供的身份范围，这里只有 tenant。两者来源不同，不能把模型的 tenant 字段复制到认证上下文。

toolRegistry 是允许执行的工具表。每个条目包含参数 Schema、结果 Schema 与 execute。Schema 描述规则，safeParse 实际执行规则，success=false 时不能继续取 data 并调用工具。

### 按处理顺序拆开 dispatchToolCall

1. 用 name 查注册表，未知工具直接返回 UNKNOWN_TOOL。
2. JSON.parse 解析 arguments，语法错误返回 INVALID_JSON。
3. 参数 Schema 检查 ticketId 是否为 T-数字；数字42会被拒绝。
4. execute 查询时同时限定工单编号与可信租户。
5. 校验实际结果，返回同一个 callId；内部未知异常只暴露受控错误码。

~~~js
const rawResult = await registeredTool.execute(
  validatedArguments.data,
  authenticatedContext,
);
~~~

这里才是真正执行的位置。你审查 AI 生成的代码时，先找到这一行，再倒推此前是否完成校验与授权。

### 追踪四条提议

|调用|进入 execute 吗|结果|
|---|---|---|
|c1：A查T-42|是|返回open|
|c2：未知工具|否|UNKNOWN_TOOL|
|c3：ticketId是数字|否|INVALID_ARGUMENTS|
|c4：B查A的工单|是，带B范围查询|NOT_FOUND_OR_FORBIDDEN|

executionAttempts=2 表示进入了两次查询函数，不表示执行了两次越权操作。c4 的查询范围限制使它读不到 A 的记录。后续真实数据库也必须保留这一条件。

### 带提示的练习

先补非法 JSON 用例，验证计数不变。再让工具返回不合约字段，观察结果校验。最后画出调用标识如何从提议流到结果；如果模型一轮提出两个同名工具，仅按工具名关联会混淆。

## 2. 先为一个只读工具写窄契约

getTicket 只接收 ticketId，不接收任意 SQL、文件路径或可调用函数名。返回 id/status，不默认返回整行数据库。用 strict 对象拒绝未约定字段，可以让“模型偷偷传一个 tenant”显式失败。

身份放在服务端 context，它来自认证中间件。在本实验中用常量模拟身份，必须明确它不是已接入真实登录。工具出错也要保留 callId，使模型与日志知道哪一项提议失败。

## 3. 实现并运行分发器

**选做本地验证：**运行 node examples/tutorials/S2-L01.mjs。先预测四次调用的结果，再运行核对。这里真正调用了业务函数，但提议本身是夹具。

### 完整实操文件：S2-L01.mjs

~~~js file=S2-L01.mjs
import assert from "node:assert/strict";
import { z } from "zod";

// 模型只提供 ticketId；租户身份由应用上下文提供，不能放进可自由修改的参数。
const ticketArgumentsSchema = z
  .object({
    ticketId: z.string().regex(/^T-\d+$/),
  })
  .strict();
const ticketResultSchema = z
  .object({
    id: z.string(),
    status: z.enum(["open", "closed"]),
  })
  .strict();

const fixtureTickets = [{ id: "T-42", tenant: "A", status: "open" }];
let executionAttempts = 0;
const toolRegistry = new Map([
  [
    "getTicket",
    {
      argumentsSchema: ticketArgumentsSchema,
      resultSchema: ticketResultSchema,
      execute(argumentsValue, authenticatedContext) {
        executionAttempts += 1;
        const ticket = fixtureTickets.find(
          (candidate) =>
            candidate.id === argumentsValue.ticketId &&
            candidate.tenant === authenticatedContext.tenant,
        );
        if (!ticket) {
          throw new Error("NOT_FOUND_OR_FORBIDDEN");
        }
        return { id: ticket.id, status: ticket.status };
      },
    },
  ],
]);

const publicErrorCodes = new Set([
  "UNKNOWN_TOOL",
  "INVALID_JSON",
  "INVALID_ARGUMENTS",
  "INVALID_TOOL_RESULT",
  "NOT_FOUND_OR_FORBIDDEN",
]);

async function dispatchToolCall(call, authenticatedContext) {
  try {
    // 第一道边界：只允许调用注册过的工具。
    const registeredTool = toolRegistry.get(call.name);
    if (!registeredTool) {
      throw new Error("UNKNOWN_TOOL");
    }

    // 第二道边界：参数文本先解析，再做实际字段校验。
    let parsedArguments;
    try {
      parsedArguments = JSON.parse(call.arguments);
    } catch {
      throw new Error("INVALID_JSON");
    }
    const validatedArguments =
      registeredTool.argumentsSchema.safeParse(parsedArguments);
    if (!validatedArguments.success) {
      throw new Error("INVALID_ARGUMENTS");
    }

    // 第三道边界：真正执行时仍受可信上下文和资源权限约束。
    const rawResult = await registeredTool.execute(
      validatedArguments.data,
      authenticatedContext,
    );
    const validatedResult = registeredTool.resultSchema.safeParse(rawResult);
    if (!validatedResult.success) {
      throw new Error("INVALID_TOOL_RESULT");
    }

    return { callId: call.id, ok: true, data: validatedResult.data };
  } catch (error) {
    // 未知内部错误不直接暴露堆栈、SQL 或连接信息。
    const code = publicErrorCodes.has(error.message)
      ? error.message
      : "TOOL_EXECUTION_FAILED";
    return { callId: call.id, ok: false, code };
  }
}

const validProposal = {
  id: "c1",
  name: "getTicket",
  arguments: '{"ticketId":"T-42"}',
};
const validResult = await dispatchToolCall(validProposal, { tenant: "A" });
assert.equal(validResult.data.id, "T-42");

const unknownToolResult = await dispatchToolCall(
  { ...validProposal, id: "c2", name: "dropAll" },
  { tenant: "A" },
);
assert.equal(unknownToolResult.code, "UNKNOWN_TOOL");

const invalidArgumentResult = await dispatchToolCall(
  { ...validProposal, id: "c3", arguments: '{"ticketId":42}' },
  { tenant: "A" },
);
assert.equal(invalidArgumentResult.code, "INVALID_ARGUMENTS");

const deniedResult = await dispatchToolCall(
  { ...validProposal, id: "c4" },
  { tenant: "B" },
);
assert.equal(deniedResult.code, "NOT_FOUND_OR_FORBIDDEN");
assert.equal(deniedResult.callId, "c4");
// 成功查询与带授权范围的拒绝查询进入 execute，其他两条在之前被拦截。
assert.equal(executionAttempts, 2);
console.log("valid / unknown / invalid args / wrong tenant: passed");
console.log("invalid proposals never reached execute; result kept callId");
~~~

## 4. 沿着执行边界读代码

toolRegistry 是允许列表，不能根据任意字符串访问全局对象。参数校验在 execute 之前，所以非法参数没有产生业务调用。execute 根据可信 authenticatedContext 过滤数据；“找不到或无权限”合并提示可以减少对资源存在性的探测，日志中仍可按授权策略记录内部原因。

输出也验证，因为业务工具或外部系统可能返回不合约结果。catch 的教学实现把错误包装为数据；生产中应使用受控错误类型与安全信息，不把任意内部 exception.message 直接回给模型。

executionAttempts=2 包含正常和无权限尝试：这是本例在业务函数内部检查资源范围的结果。若涉及写操作，应在产生副作用之前完成授权，不能先写再判断。

## 5. 把提议适配到真实服务商

内部保留 callId/name/arguments，把一家服务实际输出映射为它；结果回传再由适配器生成该服务要求的消息。不要把角色名、工具参数文本、结果字段等协议细节散落在业务工具中。

工具描述应说明何时调用、参数含义、返回上限与无结果行为。描述不清会增加模型选择错误，但即使描述完美，应用仍执行校验与授权。工具调用参数符合 JSON Schema，也不等于这次操作得到用户授权。

## 6. 亲自破坏并修复

移除 strict 后，增加 tenantId 字段，检查“额外字段”的策略是否发生变化。把 ticket 查询中的 tenant 条件删除，第四条断言应失败；不要通过隐藏前端入口修复服务端越权。

把返回 status 改成 unknown，观察输出校验失败。分清这是业务工具违反契约，不是输入 JSON 解析失败。最后给日志增加 taskId/callId/tool/version，保留足够关联而不暴露敏感正文。

## 单页速记

- 模型给提议，应用负责执行与授权。
- 名称允许列表、输入验证、可信身份、输出验证、callId 关联缺一不可。
- 工具越窄，责任越清楚；不要暴露任意 SQL/命令。
- 固定提议能测执行路径，不能测模型选工具准确率。
