# S2-L02 让助手决定下一步：什么是 Agent 循环

## 先说我们要解决什么问题

用户发来一句：“T-42 工单里说订单页白屏。帮我找排查说明，写一份回复草稿，先不要发送。”

如果你自己做，会先读工单，看是否需要查说明；查到说明后，再决定材料够不够；够了就写草稿，不够就继续查或追问信息。你不会在开始时就知道每一次操作的全部细节，而是看过前一步的结果，再决定下一步。

这节课学的就是怎样把这个过程写进应用。先看懂“决定 → 做事 → 看结果 → 再决定”，然后才谈次数、费用、超时。你现在不用先懂任何 Agent 框架。

## Agent 到底是什么意思

在这门课程中，Agent 指一种应用组织方式：**让模型根据当前任务和已有结果，提议下一步；由应用检查并执行允许的操作，再把实际结果交回去。**

模型负责提议，不直接获得数据库和发送消息的权力。应用负责执行规则。所谓“工具”，先把它理解成应用提供的普通函数，例如查文档、读工单。它不是模型凭空创造的能力。

“循环”是因为应用可能需要多次请求决定。查文档前不知道文档里写什么，得到结果后再决定要不要继续，这就需要回到前面的“决定”步骤。不是让模型自己无限运行，也不是把同一句话无休止地重问。

## 先和两种熟悉做法比较

|做法|下一步由谁决定|例子|
|---|---|---|
|普通一次问答|应用只请求一次回答|输入一段文字，拿回摘要|
|固定流程，常叫 Workflow|程序事先写好步骤|总是先分类，再检索，再生成|
|Agent 循环|模型看中间结果提议，程序控制执行|资料不足时再查，资料足够时结束|

如果流程已经固定，先用固定流程更容易理解和验证。Agent 不代表“更高级所以一定要用”，而是适合下一步需要根据中间结果变化的任务。

## 本课先做一个很小的版本

为了把流程看清，我们暂时不用真实模型。用 chooseNextAction 这个普通函数代替它：没有查过文档时提议查一次；看见文档结果后返回草稿。文档也固定返回，不访问互联网。

这份替身不是智能实现。它让你可以每次得到相同结果，专心观察应用怎样执行循环。之后 S7-L04 再讲如何把真实服务响应转换成应用能处理的结果。

~~~text
用户任务
  ↓
第一轮：决定查文档
  ↓
应用调用 searchDocs，拿到真实函数结果
  ↓
把结果放进 history
  ↓
第二轮：决定材料足够，返回草稿
  ↓
结束，不发送消息
~~~

## 这些名字与字段从哪里来

下面的字段是**我们为课堂内部交互设计的约定**，不是 JavaScript、OpenAI 或 MCP 强制规定的通用字段。接真实服务时，要由适配器把服务商格式转换成它。

|名字或字段|用普通话解释|谁创建、谁读取|
|---|---|---|
|history|已经执行过的工具和实际结果；不是模型隐藏的思考过程|应用写入，下轮决策时读取|
|decision|这轮收到的行动提议|决策函数返回，循环读取|
|type|提议属于哪一种：tools 表示请求工具，final 表示结束回答|本课约定，应用据此分支|
|calls|本轮希望调用哪些工具；这里仅放一个|决策函数填写，应用逐个处理|
|id|给这次具体工具调用起的编号，如 call-1|提议携带，应用用它关联结果|
|name|允许调用的函数名称，如 searchDocs|应用注册，提议只能选择|
|callId|结果对应前面哪次调用的 id|应用在保存结果时写入|
|result|函数实际返回的资料|应用执行得到，不能由模型伪造“已执行”|
|text|准备显示的最终草稿|决策函数返回，应用显示|
|maxRounds / round|最多允许几轮 / 现在第几轮|程序自己的变量，用来防止无限继续|

不要把变量和协议混在一起：round 只是循环计数，不是模型自动返回的“思考轮数”。这些名称可以换，但输入输出约定和执行边界必须一致。

## 用具体数据走两轮

第一轮开始时 history=[]。chooseNextAction 发现没有资料，返回 type=tools。应用调用 searchDocs 得到一段排查说明，再保存 {callId:"call-1",result:"…排查说明"}。history 现在有1项。

第二轮把这份 history 再交给决策器。因为已经有资料，它返回 type=final 和草稿。程序显示草稿并 break，不再查文档，也没有发送任何回复。

~~~text
第1轮决定：tools
应用执行工具得到：白屏排查：先收集浏览器控制台报错和最近发布的版本。
第2轮决定：final
回复草稿：请补充控制台报错和最近发布版本，我会继续定位。
~~~

这里实际只有一次工具执行、两轮决定。先能解释这个差别，才容易理解为什么“最多三轮”不一定等于“最多三个工具”。

## 什么时候再加预算、取消和复杂状态

先设想决策器每次都要求查文档。没有次数上限，应用可能永远继续。本例 maxRounds=3 给出了最简单的程序上限；完整实现进一步区分模型轮次、工具次数与总期限。

再设想一次模型请求永远不返回。只在 for 的下一轮检查次数没有用，因为程序还卡在这一轮等待。S1-L02 的取消信号和本课进阶实现一起处理这个问题。

最后才考虑费用、并行工具、失败重试和持久恢复。它们是加在这个最小循环上的工程控制，不是理解 Agent 定义的前置条件。

## 在网页里完成三件小事

1. 不运行，先说明 history 从空数组变成一项发生在哪一行。
2. 让决策器每次都提议查文档，预测最多查几次，再运行；检查为什么不应该把预算停止显示成成功答案。
3. 用自己的话解释：模型提议、应用执行、历史记录各是谁负责的。只说“Agent 会自动调用工具”还不够。
