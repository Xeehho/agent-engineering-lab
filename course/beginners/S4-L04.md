# S4-L04 先查再改，为什么可能覆盖别人

## 先说我们要解决什么问题

两个工作者都读到任务version=1，然后分别保存修改。如果后保存的一方不检查版本，就会覆盖先保存的结果。

## 先把概念讲清楚

SQL是操作关系数据库的语言，表是一组按列约定的记录。索引为特定查询维护查找结构，会占空间并增加写入成本；不是越多越好。事务把一组数据库操作作为一个提交单元，具体隔离级别决定并发可见性与冲突行为。

乐观并发控制是保存时检查“我读到的版本仍然是当前版本吗”。SQL可把检查与更新写进同一语句：UPDATE tasks SET version=version+1 ... WHERE id=? AND version=?，再检查实际改了几行。

## 名字与字段从哪里来

|名字或字段|来源与含义|
|---|---|
|row / version|课堂模拟一行记录与修改版本|
|expectedVersion|调用方读到的旧版本，不能直接当当前版本|
|save|课堂原子步骤的顺序模拟；不是数据库事务|
|updated rows / UNIQUE|SQL返回的修改行数概念与唯一约束；真实语法看选用数据库|

~~~text

~~~

A保存时版本仍为1，成功后变2；B带着旧1来保存时不匹配，所以不覆盖。浏览器顺序演示没有验证数据库锁和实际并发。进阶使用真实SQLite条件更新与事务，再考虑PostgreSQL等数据库的隔离差异。数据库事务也不能自动覆盖外部邮件API。
