# S3-L03 MCP 权限、缓存与服务信任

上一课证明协议互通，这一课验证“谁能读到什么”。实验使用 SQLite 与合成认证上下文，不实现 OAuth 或真实登录；它不代表远程认证已经安全，也不代表学习者已掌握。

## 1. 两条独立的信任线

你信任某个 Server 的维护者与代码，不意味着每个调用者都能读它的数据。服务来源、版本、运行权限是一条线；用户身份、租户、资源与操作授权是另一条线。两者都要成立。

模型参数 tenant=B 只是一段输入，不能替代服务端认证。MCP 的工具描述和返回文本也属于外部内容，不能自动取得 Host 的执行权限。远程 Token 需要校验签发者、受众、范围与期限，不能把本应用凭证随意透传到另一个 Server。

## 3. 代码保证与剩余假设

权限检查发生在缓存命中之前，所以权限撤回后不能沿旧结果直接返回。policyVersion 可帮助改变策略后隔离缓存，但版本必须由服务端治理。若资源 ACL 发生变化，还需要资源权限版本、主动失效或短 TTL；不能认为加入一个字段就解决所有撤权时效问题。

字段白名单在 SQL 层先不取 internal_note，减少敏感数据进入进程和日志。返回对象再复制，防止调用方修改共享缓存对象。更复杂的字段级权限需要不同结果范围与缓存键，不能只看租户。

参数化 SQL 防止值被当成语法，但不自动完成业务授权。多租户过滤如果忘了写，参数化查询仍会忠实地返回错误范围的数据。

## 4. Server 安装前的最小审查

列出它能读的目录、网络端点、环境变量、数据库账号和写操作。把“只读工单”的 Server 放在能访问所有本机文件和生产密钥的进程中，会扩大故障半径。凭证按服务受众与最小权限配置，避免把整个环境继承给未知子进程。

记录维护者、来源、固定版本与升级差异。工具描述更新可能改变模型选择行为，即使程序接口未变，也需要回归。声明 readOnlyHint 等元数据有助于 UI，但它不是强制授权，Host 不能只相信服务自报。

## 故障练习与项目迁移

先把缓存键改成 args.id，验证 B 读到 A 的标题；再去掉 SQL 的 tenant 条件，看正确缓存也无法挽救错误查询。最后给 A 撤回 scope，验证缓存命中路径仍拒绝。

项目中把 read 放到 MCP handler 后端，并从真实认证中间件取 auth，工具 Schema 不开放 tenant、role 或 scopes。提交正常、越权、撤权、缓存串用、字段泄露、污染输出六类证据。只做课堂合成 auth 时，报告里明确认证尚未接入。

## 单页速记

- 服务可信与用户有权限分别判断。
- 身份来自认证上下文，资源查询带授权范围。
- 缓存不是绕过授权的入口，撤权与版本要有失效策略。
- 工具描述、输出文本和注解不能自行提升权限。
