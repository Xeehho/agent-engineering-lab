# S2-L01｜工具调用：从模型提议走到真实、受控的业务执行

教材已扩写，不代表学习者已经掌握。环境：Node 24，仓库锁定的 Zod。使用合成工单与固定模型提议；不声称验证了真实模型选工具的能力。

## 本课目标

- 实现提议、解析、授权、执行、结果关联的完整小路径。
- 通过未知工具、非法参数与越权案例理解执行边界。
- 把服务商消息格式与内部业务契约分开。

## 1. 模型为什么不能直接调用你的函数

模型返回 getTicket({ticketId:"T-42"}) 时，本质上给出了名称和参数。它没有获得服务器函数指针，也没有因为写出 tenantId 就自动变成那个租户的用户。应用必须决定这个操作是否存在、参数是否可接收、当前身份是否有权执行。

五步路径是：向模型描述可用工具；收到工具提议；应用校验并执行；把真实结果关联回 callId；模型继续或生成最终回答。不同服务的消息字段不同，但应用的责任不会消失。

## 2. 先为一个只读工具写窄契约

getTicket 只接收 ticketId，不接收任意 SQL、文件路径或可调用函数名。返回 id/status，不默认返回整行数据库。用 strict 对象拒绝未约定字段，可以让“模型偷偷传一个 tenant”显式失败。

身份放在服务端 context，它来自认证中间件。在本实验中用常量模拟身份，必须明确它不是已接入真实登录。工具出错也要保留 callId，使模型与日志知道哪一项提议失败。

## 3. 实现并运行分发器

运行 node examples/tutorials/S2-L01.mjs。先预测四次调用的结果，再运行核对。这里真正调用了业务函数，但提议本身是夹具。

~~~js file=S2-L01.mjs
import assert from "node:assert/strict";
import { z } from "zod";
const argsSchema = z.object({ticketId:z.string().regex(/^T-\d+$/)}).strict();
const resultSchema = z.object({id:z.string(),status:z.enum(["open","closed"])}).strict();
const tickets = [{id:"T-42",tenant:"A",status:"open"}];
let executions = 0;
const registry = new Map([["getTicket", {
  args:argsSchema, result:resultSchema,
  execute(args,ctx) {
    executions++;
    const ticket = tickets.find(t=>t.id===args.ticketId && t.tenant===ctx.tenant);
    if (!ticket) throw new Error("NOT_FOUND_OR_FORBIDDEN");
    return {id:ticket.id,status:ticket.status};
  }
}]]);
async function dispatch(call,ctx) {
  try {
    const tool = registry.get(call.name);
    if (!tool) throw new Error("UNKNOWN_TOOL");
    const args = tool.args.safeParse(JSON.parse(call.arguments));
    if (!args.success) throw new Error("INVALID_ARGUMENTS");
    const value = await tool.execute(args.data,ctx);
    return {callId:call.id,ok:true,data:tool.result.parse(value)};
  } catch(error) {
    return {callId:call.id,ok:false,code:error instanceof SyntaxError?"INVALID_JSON":error.message};
  }
}
const proposal = {id:"c1",name:"getTicket",arguments:'{"ticketId":"T-42"}'};
assert.equal((await dispatch(proposal,{tenant:"A"})).data.id,"T-42");
assert.equal((await dispatch({...proposal,id:"c2",name:"dropAll"},{tenant:"A"})).code,"UNKNOWN_TOOL");
assert.equal((await dispatch({...proposal,id:"c3",arguments:'{"ticketId":42}'},{tenant:"A"})).code,"INVALID_ARGUMENTS");
const denied = await dispatch({...proposal,id:"c4"},{tenant:"B"});
assert.equal(denied.code,"NOT_FOUND_OR_FORBIDDEN");
assert.equal(denied.callId,"c4");
assert.equal(executions,2);
console.log("valid / unknown / invalid args / wrong tenant: passed");
console.log("invalid proposals never reached execute; result kept callId");
~~~

invalid proposals never reached execute; result kept callId
~~~

## 4. 沿着执行边界读代码

registry 是允许列表，不能根据任意字符串访问全局对象。参数 parse 在 execute 之前，所以非法参数没有产生业务调用。execute 根据可信 context 过滤数据；“找不到或无权限”合并提示可以减少对资源存在性的探测，日志中仍可按授权策略记录内部原因。

输出也验证，因为业务工具或外部系统可能返回不合约结果。catch 的教学实现把错误包装为数据；生产中应使用受控错误类型与安全信息，不把任意内部 exception.message 直接回给模型。

executions=2 包含正常和无权限尝试：这是本例在业务函数内部检查资源范围的结果。若涉及写操作，应在产生副作用之前完成授权，不能先写再判断。

## 5. 把提议适配到真实服务商

内部保留 callId/name/arguments，把一家服务实际输出映射为它；结果回传再由适配器生成该服务要求的消息。不要把角色名、工具参数文本、结果字段等协议细节散落在业务工具中。

工具描述应说明何时调用、参数含义、返回上限与无结果行为。描述不清会增加模型选择错误，但即使描述完美，应用仍执行校验与授权。工具调用参数符合 JSON Schema，也不等于这次操作得到用户授权。

## 6. 亲自破坏并修复

移除 strict 后，增加 tenantId 字段，检查“额外字段”的策略是否发生变化。把 ticket 查询中的 tenant 条件删除，第四条断言应失败；不要通过隐藏前端入口修复服务端越权。

把返回 status 改成 unknown，观察输出校验失败。分清这是业务工具违反契约，不是输入 JSON 解析失败。最后给日志增加 taskId/callId/tool/version，保留足够关联而不暴露敏感正文。

## 项目迁移与验收

为项目新增 getTicket 与 searchDocs 两个只读工具，先写 Schema、身份来源、允许范围、失败类型与返回上限。画出模型适配器与业务分发器的边界，再实现。

至少提交正常、未知工具、非法 JSON、字段错误、越权和工具输出错误六条用例。本人解释其中一次拒绝发生在什么位置。真实模型提议质量与本地分发正确性分别记录；本课不替你实现完整 Agent。

## 单页速记

- 模型给提议，应用负责执行与授权。
- 名称允许列表、输入验证、可信身份、输出验证、callId 关联缺一不可。
- 工具越窄，责任越清楚；不要暴露任意 SQL/命令。
- 固定提议能测执行路径，不能测模型选工具准确率。
