## 代码阅读：报告里的 passed 从哪里来

### 两个函数分别负责什么

parseNonNegativeCount 输入 JSON 文本，成功返回非负整数，失败抛出原因。runContractCase 输入一条事先定义的用例，实际调用前者，再比较 actual 与 expected。业务逻辑和报告逻辑分开后，你可以单独定位“实现错了”还是“评分规则错了”。

expected 是需求的表达，必须先写。actual 来自真正执行的返回值或异常。若直接把 expected 复制给 actual，再漂亮的报告也没有验证价值。

### 用一个输入走完整条路径

~~~js
const jsonText = '{"count":"2"}';
const parsedValue = JSON.parse(jsonText);
console.log(typeof parsedValue.count); // string
console.log(Number.isInteger(parsedValue.count)); // false
~~~

JSON.parse 没有把双引号中的2转成整数。parseNonNegativeCount 因此抛出 INVALID_COUNT，runContractCase 捕获异常并把错误码记录为 actual。预期也恰好是 INVALID_COUNT，所以这条拒绝用例通过；通过的含义是“正确拒绝了非法数据”。

|用例|实际运行得到|为何通过|
|---|---|---|
|normal|数字2|与预期数字相同|
|string|INVALID_COUNT|正确拒绝字符串|
|null|NOT_OBJECT|在读取字段之前拒绝外层值|
|negative|INVALID_COUNT|正确拒绝负数|

### 怎样读断言

assert.equal(actual, expected) 不相等就抛异常，进程失败。这里汇总通过数，是为了让脚本在任何一条失败时退出非零；控制台打印只是给人看。之后要追查失败原因，应查看 evidenceRows 中的具体输入与实际结果，而非只盯住总数。

本例将返回值和错误码放在同一 actual 字段，是因为数字与错误字符串能清楚区分。更复杂的系统应使用结构化结果，例如 ok/data 或 ok/code，避免“返回的字符串刚好等于错误码”。

### 带提示的练习

先增加 count=0 的用例，不改实现，预测是否通过。再增加损坏 JSON，决定是否保留原始解析错误还是映射统一错误码。最后删除负数检查，保存失败记录，并根据契约修复，不能改 expected 迎合错误实现。
