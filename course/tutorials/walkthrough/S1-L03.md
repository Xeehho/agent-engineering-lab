## 代码阅读：把解码、分帧、校验和状态拆开

### 四个输入输出边界

parseEventChunks 输入 Uint8Array 数组，输出通过字段校验的事件数组。validateEvent 输入 JSON.parse 得到的未知值，拒绝 null、数组、缺字段与未知类型。reduceStreamEvent 输入旧状态和一个事件，返回新状态；它不读取网络，也不处理字节。

这是课堂自定义 delta/done 契约，用于学习增量文字。第一阶段工单项目的 started/completed/failed 契约用于完整分诊结果。接项目时需要显式映射，不能因为都采用 SSE 风格分隔就直接混用。

### 为什么要有两份缓冲

“订”在 UTF-8 中占多个字节，拆成单字节后，decoder 需要暂存没凑齐的字符。解码出的文字还可能只有半个 JSON，unconsumedText 则暂存没有凑齐的消息。前者解决字符，后者解决协议帧，职责不同。

~~~js
// separatorIndex 之前是一条完整帧；之后仍可能是半条或多条帧。
const completeFrame = unconsumedText.slice(0, separatorIndex);
unconsumedText = unconsumedText.slice(separatorIndex + 2);
~~~

这里加2是因为分隔符由两个换行组成。消费后重新查找分隔符，while 才能处理一次读取中的多条事件。结束时执行 decoder.decode() 检查尾部字符，再检查文本缓冲是否残留。

### 手工追踪 reducer

|到达的事件|之前状态|之后文字|之后状态|
|---|---|---|---|
|r1 的 delta：订单|running|订单|running|
|r1 的 done|running|订单|succeeded|
|r1 的 delta：旧结果|succeeded|订单|succeeded|
|旧 runId 的事件|当前r1|保持原值|保持原值|

React 中可使用同样的 reducer 思路。每次输入新任务，先创建新 runId 与初始状态，再消费已校验事件。函数式更新解决读取旧文本的问题；runId 判断解决旧请求污染新请求的问题，两者需要分别实现。

### 带提示的练习

先把整段字节作为一个 chunk，再按单字节拆分，预测两种结果应一致。把 while 改成 if，观察整包场景为什么失败。先只给 parser 添加错误事件校验，再单独给 reducer 添加失败终态，不要同时改网络、解析器和组件后再猜是哪层出错。
