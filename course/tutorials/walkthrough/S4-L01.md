## 代码阅读：数据库怎样拒绝旧状态

### 先读表，再读函数

tasks 保存当前快照：id 是任务身份，state 是当前状态，version 每次合法转换加1。events 保存每次转换；同任务同版本只能有一条。快照方便查询，事件方便回放，两者必须保持一致。

transitionTask(taskId,expectedVersion,nextState) 要求调用方说明“我依据哪个版本做决定”。expectedVersion 不是服务器自己随便填最新值，否则旧调用者也能冒充最新判断。

### 用版本追踪同一任务

|调用|当前数据库|检查结果|
|---|---|---|
|版本0请求running|queued，版本0|成功，版本变1|
|重新打开数据库|running，版本1|仍可读取|
|旧版本0请求succeeded|running，版本1|STALE_VERSION|
|版本1请求succeeded|running，版本1|成功，版本变2|
|版本2请求failed|succeeded，版本2|ILLEGAL_TRANSITION|

### SQL 中的条件有什么用

~~~sql
UPDATE tasks
SET state = ?, version = version + 1
WHERE id = ? AND version = ?;
~~~

run(nextState,taskId,expectedVersion) 与问号按顺序对应。changes=1 表示这一行确实被修改；0表示条件没有匹配。不要执行完 UPDATE 就直接宣布成功。

任务更新与事件插入放在同一事务，任一步失败就回滚。终态保护来自 allowedTransitions，不是“页面上不再显示按钮”。前端用相同任务ID与递增版本消费事件；发现版本缺口时重新拉快照。

### 带提示的练习

先预测旧版本为什么失败，再删除版本条件复现覆盖。把事件插入移到事务外并制造失败，检查快照与事件如何不一致。重启恢复只证明状态还在，下一步是否重跑仍要检查副作用和租约。
