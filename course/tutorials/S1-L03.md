# S1-L03｜流式事件：从字节碎片到可信的 React 状态

教材已扩写，不代表学习者已经掌握。运行环境 Node 24；本课构造真实编码字节并任意拆包，不连接模型。先修：Promise、取消、对象契约。

## 本课目标

- 解释 UTF-8 解码、消息分帧、业务校验、状态更新四个步骤。
- 在任意拆包下得到相同事件，并拒绝终态后的旧数据。
- 说明 HTTP 头发送前后错误处理为何不同。

## 1. 为什么一次 read 不能直接 JSON.parse

模型接口开始逐步显示文字，最容易写出的代码是：每读到一个 chunk 就解码、JSON.parse、setText。问题在于网络不理解你的对象边界。

例如 data: 后的一个 JSON 可以分成三段，中文“订单”又可能在多字节字符中间被截断。反过来，一次读取也可能同时包含 delta、done 两个完整事件。因此解析器必须保留未消费的缓冲，不能把 chunk 当作事件。

~~~text
字节流 → 流式 UTF-8 解码 → 文本缓冲/分帧 → JSON与字段校验 → 带 runId 的 reducer
~~~

这五步任何一步失败，都应有明确的停止与错误状态，而不是继续把残缺结果显示为“完成”。

## 2. 先限定今天实现的协议子集

这里采用 SSE 风格的 data: 单行 JSON + 空行分隔，只支持本课写明的子集。真正 SSE 还涉及 CRLF、多行 data、注释、id/retry 和重连，不能把教学解析器直接称作完整标准实现。

原生 EventSource 与 fetch 的接口能力不同。需要 POST 请求体时，可以用 fetch 消费响应体，但需自己处理对应消息格式。你还必须明确自己的后端事件契约，而不是把不同模型厂商的流式字段直接扔给页面。

## 3. 分步实验：把每个字节都拆成一个 chunk

下面先建立消息，再编码，最后故意按单字节读取。这是最小的确定性拆包压力案例。保存或下载脚本后，在根目录运行 node examples/tutorials/S1-L03.mjs。

~~~js file=S1-L03.mjs
import assert from "node:assert/strict";
const source = [
  {runId:"r1", type:"delta", text:"订单"},
  {runId:"r1", type:"done"},
  {runId:"r1", type:"delta", text:"旧结果"}
].map(event => "data: " + JSON.stringify(event) + "\n\n").join("");
const bytes = new TextEncoder().encode(source);

function parse(chunks) {
  const decoder = new TextDecoder("utf-8", {fatal:true});
  let buffer = "";
  const events = [];
  for (const chunk of chunks) {
    buffer += decoder.decode(chunk, {stream:true});
    let end;
    while ((end = buffer.indexOf("\n\n")) >= 0) {
      const frame = buffer.slice(0,end); buffer = buffer.slice(end+2);
      if (!frame.startsWith("data: ")) throw new Error("BAD_FRAME");
      const event = JSON.parse(frame.slice(6));
      if (event.runId !== "r1" || !["delta","done"].includes(event.type))
        throw new Error("BAD_EVENT");
      if (event.type === "delta" && typeof event.text !== "string")
        throw new Error("BAD_DELTA");
      events.push(event);
    }
  }
  buffer += decoder.decode();
  if (buffer.trim()) throw new Error("INCOMPLETE_FRAME");
  return events;
}
const whole = parse([bytes]);
const split = parse(Array.from(bytes, byte => Uint8Array.of(byte)));
assert.deepEqual(split,whole);
let state = {runId:"r1",status:"running",text:""};
for (const event of split) {
  if (event.runId !== state.runId || state.status !== "running") continue;
  state = event.type === "delta"
    ? {...state,text:state.text+event.text}
    : {...state,status:"succeeded"};
}
assert.equal(state.text,"订单");
assert.equal(state.status,"succeeded");
assert.throws(() => parse([bytes.slice(0,-1)]), /INCOMPLETE_FRAME/);
console.log("whole packet = byte-by-byte packet");
console.log("text=订单; terminal protected; truncated frame rejected");
~~~

~~~text expect=S1-L03.mjs
whole packet = byte-by-byte packet
text=订单; terminal protected; truncated frame rejected
~~~

## 4. 为什么这几行不能省略

decoder.decode 的 stream:true 保留未完成字符；最后再调用一次无参数 decode 刷出尾部状态。fatal:true 让无效 UTF-8 成为错误，而不是默默用替代字符污染结果。

buffer 只删除已经消费的帧。while 而不是 if，保证一次 chunk 内多个事件都被处理。流结束时还有残余，不能悄悄忽略；它可能意味着截断。JSON.parse 后仍校验事件字段，避免合法 JSON 中缺少 text。

reducer 接受的是已验证事件，而不是原始字节。只有当前 runId 且仍为 running 才更新。第三条 delta 正好用来证明“终态后不更新”，不证明实际服务器不会发送它。

## 5. 接到 React 时先定义状态，再写组件

用 idle/running/succeeded/failed/cancelled 表达任务。每次新请求分配新的 runId，在 reducer 或更新函数中检查身份；函数式状态更新可以避免闭包拿到旧文本，但不能替代 runId 检查。

快速 token 到达时可以按帧或短缓冲批量刷新，而不是无边界累加。显示“部分输出”和“完整结果”的样式要区分；取消或失败后保留多少内容也要提前约定。读取流的 finally 释放 reader、处理取消，不把网络结束自动解释为业务成功。

## 6. 分别处理两类失败

HTTP 头发出前，应用可以用正常错误状态和 JSON 错误体返回。头与若干 delta 发出后，再写一套 500 JSON 会破坏已经约定的流；需要流内 error 事件、终止与日志关联。

断网后是否重连、从哪个 eventId 恢复、已显示事件怎样去重，都属于额外契约。SSE 传输的重连能力不等于你的业务任务可恢复，更不等于写入工具会被正确去重。

## 7. 故障注入与定位顺序

把 while 改成 if，再用整个 bytes 一次送入，观察会漏消费帧。移除 stream:true，再按单字节拆中文，观察解码异常。移除 reducer 的终态判断，观察“旧结果”进入最终文本。

定位顺序是先看原始字节与帧边界，再看字段校验，最后看业务状态。不要一看到文字重复就先改 CSS 或换模型。

## 练习与验收

1. 支持 CRLF 和两行 data，先写输入与期望，再实现；说明与完整 SSE 仍有哪些差距。
2. 增加 error、cancelled 终态，测试重复终态、旧 runId 和终态后 delta。
3. 将解析与 reducer 分离到独立模块，再接项目的 React 面板；保留真实浏览器取消和服务端日志。

验收要求任意拆包/合包一致、非法帧失败明确、终态唯一、旧结果不能覆盖新请求。课堂单测通过不代替真实网络重连测试。

## 单页速记

- chunk 不等于消息；字符也会跨 chunk。
- 流式解码、缓冲分帧、字段校验、状态更新分别处理。
- 头前用 HTTP 错误，头后用协议内错误。
- 网络结束、完整消息与任务成功不是同一个状态。
