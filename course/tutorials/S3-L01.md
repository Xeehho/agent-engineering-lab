# S3-L01 MCP：把角色图变成真实互通

本课使用已锁定的 @modelcontextprotocol/sdk 1.32.2 与 Zod 4.6.7。该 SDK 的默认协议修订是 2025-11-25，不把新版网站的修订号套到旧 SDK。实验有真实子进程、初始化、发现与工具调用；没有模型或远程服务，教材完成不代表学习者已掌握。

## 1. 先按职责拆开

想象研发助手界面收到“查 T-42”。Host 管理界面、模型、用户身份、工具批准与任务状态；Client 是 Host 内说 MCP 协议的组件；Server 暴露工单能力。模型本身不等于 Client，MCP Server 也不自动成为会推理的 Agent。

本实验的 client 文件兼任最小 Host：它启动子进程、创建 Client、发现工具并直接指定调用。server 文件提供只读工单。真实应用会把发现的工具适配给模型，再把模型提议经过执行边界送给 Client；那部分尚未接入。

工具适合有参数的动作；资源适合可读取的上下文；提示模板用于复用交互。本课只实现工具，不宣称覆盖所有 MCP 能力。

## 2. 创建 Server

先 npm ci 安装锁定依赖。两个文件要保存到同一目录；网页可下载两份。服务端 stdout 留给协议，诊断使用 stderr。

~~~js file=S3-L01-server.mjs
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";
const server = new McpServer({name:"ticket-classroom",version:"1.0.0"});
server.registerTool("get_ticket", {
  description:"读取课堂固定工单；不提供业务写入",
  inputSchema:{ticketId:z.string().regex(/^T-\d+$/)},
  outputSchema:{id:z.string(),status:z.string()}
}, async ({ticketId}) => {
  if (ticketId !== "T-42") return {isError:true,content:[{type:"text",text:"NOT_FOUND"}]};
  const data = {id:ticketId,status:"open"};
  return {structuredContent:data,content:[{type:"text",text:JSON.stringify(data)}]};
});
await server.connect(new StdioServerTransport());
~~~

inputSchema 是输入契约，outputSchema 限定成功结果，structuredContent 方便程序读取。text 内容便于兼容展示。它们都不能替代工单授权；固定 T-42 只是数据夹具，S3-L03 再加租户边界。

## 3. 创建 Client 并验证

~~~js file=S3-L01.mjs
import assert from "node:assert/strict";
import { fileURLToPath } from "node:url";
import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { StdioClientTransport } from "@modelcontextprotocol/sdk/client/stdio.js";
import { LATEST_PROTOCOL_VERSION } from "@modelcontextprotocol/sdk/types.js";
const transport = new StdioClientTransport({
  command:process.execPath,
  args:[fileURLToPath(new URL("./S3-L01-server.mjs",import.meta.url))],
  stderr:"inherit"
});
let requested;
const send = transport.send.bind(transport);
transport.send = async message => {
  if (message.method === "initialize") requested = message.params.protocolVersion;
  return send(message);
};
const client = new Client({name:"classroom-host",version:"1.0.0"});
try {
  await client.connect(transport);
  assert.equal(LATEST_PROTOCOL_VERSION,"2025-11-25");
  assert.equal(requested,LATEST_PROTOCOL_VERSION);
  assert.equal(client.getServerVersion().name,"ticket-classroom");
  const discovery = await client.listTools();
  assert.deepEqual(discovery.tools.map(t => t.name),["get_ticket"]);
  assert.ok(discovery.tools[0].inputSchema.properties.ticketId);
  const result = await client.callTool({name:"get_ticket",arguments:{ticketId:"T-42"}});
  assert.notEqual(result.isError,true);
  assert.deepEqual(result.structuredContent,{id:"T-42",status:"open"});
  console.log("stdio initialize + tools/list + tools/call: passed");
  console.log("SDK default proposal=2025-11-25; server=ticket-classroom; T-42=open");
} finally {
  await client.close();
}
~~~

~~~text expect=S3-L01.mjs
stdio initialize + tools/list + tools/call: passed
SDK default proposal=2025-11-25; server=ticket-classroom; T-42=open
~~~

运行 npm run tutorial -- S3-L01。初始化请求被截取以核对默认提出的修订，连接与发现由 SDK 完成。教材没有把“提出的版本”谎称为通用协商日志；要审计协商结果，可在受控传输记录初始化响应，并按采用修订验证。

## 4. 用边界理解协议的价值

原来 Host 直接 import getTicket；现在 Server 可以独立运行、用另一种语言编写，被多个 Host 接入，Client 能发现描述与 Schema。代价是进程管理、版本兼容、发现缓存、超时、权限和观测。若业务始终只是同进程函数调用，暂不引入协议也合理。

连接成功只说明协议路径跑通。它没有证明模型会选对工具，也没有证明远程认证、用户授权、数据库读取或生产负载。请把这些分开写进证据记录。

## 故障练习与项目迁移

给 Server 顶部加 console.log("ready")，观察协议通道被污染；改成 console.error。把 Client 的工具名改成旧名字，区分发现清单与调用结果。关闭 server 文件路径，记录子进程启动失败，而非把它归为工单不存在。

项目练习：把 S2 的两个只读业务工具适配为 MCP，保留业务函数与协议层的分离。提交角色图、锁定版本、发现结构、一次成功调用和清理证据。本人解释“谁持有登录身份、谁检查资源权限、谁决定工具是否执行”，不能只展示安装命令。

## 单页速记

- Host 管任务与策略，Client 管连接，Server 提供能力。
- MCP 是互操作边界，不是模型、Agent 或授权系统。
- 版本按实际依赖核对；发现、调用、业务成功分别验证。
- stdio 的 stdout 是协议通道，退出时关闭 Client。
