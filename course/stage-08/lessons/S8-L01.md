# S8-L01 毕业项目先从验收边界画起

## 先说我们要解决什么问题

你想做“能处理一切的AI助手”，范围很大却很难判断什么时候算完成。面试时也只剩一段演示，没有可靠证据。

## 先把概念讲清楚

毕业项目把课程串成一个边界明确的产品，例如“有权限的工单资料检索与回复草稿助手”。先列用户、输入、允许操作、不允许操作和验收案例，再设计数据流。最小纵向切片是能从界面一路走到后端并返回结果的一条短路径；逐步加检索、工具、持久任务和评测。

作品完成与学习掌握是两种结论。AI可以帮实现，但你要能解释关键路径、修改约束、复现故障并说明证据范围。网页演示不能代替真实毕业项目。

## 名字与字段从哪里来

|名字或字段|来源与含义|
|---|---|
|requirements / evidence|课堂需求编号与证据清单|
|requirementId / scope|课堂证据关联字段；真实提交带commit、环境和复现方法|
|missing|本例没有覆盖的需求，不自动判定已覆盖项合格|
|filter / some|JavaScript集合匹配，用来检查清单完整性|

## 先读这个最小例子

网页“动手实验”运行相同代码。先找输入、检查与输出；assert 是课堂提供的检查函数，不是模型能力。

~~~js
const requirements = ["租户隔离", "可取消", "草稿不自动发送"];
const evidence = [
  { requirementId: "租户隔离", scope: "本地受控" },
  { requirementId: "草稿不自动发送", scope: "本地受控" },
];
const missing = requirements.filter(
  (id) => !evidence.some((item) => item.requirementId === id),
);
console.log("缺少证据：", missing.join("、"));
assert.deepEqual(missing, ["可取消"]);
~~~
## 运行结果与逐步解释

~~~text
缺少证据： 可取消
~~~

逐条需求寻找同编号证据，可取消没有记录所以缺失。已有记录只是有条目，不说明质量、覆盖范围和真实性合格。项目提交应让陌生开发者按README复现，区分Mock、真实组件、真实模型和未验证边界。

## 在网页里完成三件小事

1. 补可取消记录，并说明具体触发步骤。
2. 把需求拆成正常、错误、越权、重试四类验收。
3. 画从界面到工具结果再回到答案的完整路径。

## 1. 用一个真实用户路径收敛范围

用户提交问题 → 识别意图 → 授权检索工单与文档 → 生成带来源的草稿 → 人工确认 → 幂等写入 → 可追踪与恢复。先实现这条纵向路径，再考虑更多角色和功能。

需求至少写清角色、输入、可执行动作、权限、缺信息行为、失败恢复与成功证据。不要以“用了 RAG、MCP、多 Agent”作为用户价值；它们是实现选择，必须解释为什么需要。

将验收拆成可观察条件：跨租户拒绝、引用可还原、超时清理、任务重启恢复、审批变更失效、重复写不增加记录、关键回归门槛。每条绑定测试、日志或演示，而非只有一个勾。

## 代码阅读：把需求连到合适的证据

### 清单里每个字段都应有用途

requirements说明要验证什么以及需要哪类证据；evidence记录对应需求、具体commit、类型、状态与产物引用。auditEvidence逐项匹配，不让旧截图或错误类型的报告满足当前需求。

|要求|现有材料|结果|
|---|---|---|
|租户隔离|当前commit的本地测试|有匹配证据|
|重启恢复|另一commit的重启记录|暂未验证|
|模型质量|当前commit的夹具测试|暂未验证，类型不符|

补一份当前版本的重启记录后，恢复要求才变成evidenced。模型质量仍缺真实评测，不能因为其他项通过就代替它。

### 元数据检查的边界

artifact是引用，脚本尚未打开文件审阅。填一个文件名只证明清单格式满足条件，不证明材料存在或可信。实际评阅需校验产物、复现关键行为并追问本人解释。

毕业项目按一个完整用户路径逐步做：输入、授权、检索、草稿、确认、幂等写入、恢复与观测。网站内可以完成机制练习；进阶项目用来证明真实服务与交付能力。

### 带提示的练习

先把证据commit改旧，预测哪项失效。再用截图替代重启日志，说明证据类型为何不够。最后挑一项你最想写进简历的能力，列出最短的可复现验证路径。

## 2. 编写证据清单检查器

### 完整实操文件：S8-L01.mjs

~~~js file=S8-L01.mjs
// 证据需要同时匹配需求、类型和当前commit；元数据通过后仍要审阅实际产物。
import assert from "node:assert/strict";
const requirements = [
  { id: "tenant-isolation", needs: "local-test" },
  { id: "restart-recovery", needs: "restart-test" },
  { id: "model-quality", needs: "live-eval" },
];
// 把每条要求映射到证据，不把缺失或旧版本材料当成功。
function auditEvidence(requirements, evidence, targetCommit) {
  if (!/^[0-9a-f]{40}$/.test(targetCommit)) {
    throw new Error("INVALID_COMMIT");
  }
  return requirements.map((requirement) => {
    const matchingEvidence = evidence.filter(
      (evidenceRecord) =>
        evidenceRecord.requirement === requirement.id &&
        evidenceRecord.commit === targetCommit,
    );
    const hasMatchingEvidence = matchingEvidence.some(
      (evidenceRecord) =>
        evidenceRecord.kind === requirement.needs &&
        evidenceRecord.status === "passed" &&
        typeof evidenceRecord.artifact === "string" &&
        evidenceRecord.artifact.length > 0,
    );
    return {
      id: requirement.id,
      status: hasMatchingEvidence ? "evidenced" : "unverified",
    };
  });
}
const targetCommit = "a".repeat(40);
const evidence = [
  {
    requirement: "tenant-isolation",
    kind: "local-test",
    status: "passed",
    artifact: "isolation.json",
    commit: targetCommit,
  },
  {
    requirement: "restart-recovery",
    kind: "restart-test",
    status: "passed",
    artifact: "restart.log",
    commit: "b".repeat(40),
  },
  {
    requirement: "model-quality",
    kind: "fixture-test",
    status: "passed",
    artifact: "fixture.json",
    commit: targetCommit,
  },
];
let auditRows = auditEvidence(requirements, evidence, targetCommit);
assert.deepEqual(
  auditRows.map((requirement) => requirement.status),
  ["evidenced", "unverified", "unverified"],
);
evidence.push({
  requirement: "restart-recovery",
  kind: "restart-test",
  status: "passed",
  artifact: "restart-new.log",
  commit: targetCommit,
});
auditRows = auditEvidence(requirements, evidence, targetCommit);
assert.equal(auditRows[1].status, "evidenced");
assert.equal(auditRows[2].status, "unverified");
assert.throws(() => auditEvidence(requirements, evidence, "main"), /COMMIT/);
console.log(
  "current-commit isolation evidenced; stale recovery rejected then refreshed",
);
console.log(
  "fixture did not satisfy live-model quality; artifact content still needs review",
);
~~~
~~~text expect=S8-L01.mjs
current-commit isolation evidenced; stale recovery rejected then refreshed
fixture did not satisfy live-model quality; artifact content still needs review
~~~

**选做本地验证：**运行 npm run tutorial -- S8-L01。这个审计器只检查元数据，不会证明文件真实存在或内容可信。下一步需要解析报告、校验摘要并由评阅者核对关键行为。把 artifact 字段填成一个文件名并不能获得毕业资格。

## 3. 项目结构与里程碑

前端负责任务状态、流式输出、来源、审批与错误恢复；后端负责身份、执行控制、数据库、模型适配与工具；数据层负责版本、权限、索引与删除；质量层负责评测、观测与发布门槛。

第一个里程碑只做固定 workflow 和本地夹具，验证纵向路径；第二个接真实数据与检索，对照基线；第三个在授权范围接模型与评测；第四个演练恢复、部署与展示。每个里程碑都有可运行 commit 和未验证清单，不按日历自动过关。

## 4. AI Coding 的学习要求

你可以让 Agent 写代码，但要能指出可信输入在哪里、哪个函数会产生副作用、哪个条件阻止越权、超时如何传播、哪些证据支持结论。要求先预测，再运行，再解释差异，最后做一个未知变更。

保留 AI 协助范围：生成了什么、你修改了什么、你怎样验证。作品集说明 AI Coding 的工程过程比伪装手写更有说服力。考试会要求你独立解释和排查变式，不能只背这份教程的输出。

## 故障练习与项目迁移

给旧 commit 的截图贴上新版本名称，检查审计如何发现。用 fixture-test 替代 live-eval，说明为什么不满足模型质量。构造“测试通过但用户路径失败”的场景，补浏览器与请求副作用证据。

毕业交付至少有需求、架构、启动、数据与权限、评测、故障恢复、部署、演示和限制说明。实际证据未齐全时保留 unverified，不写“生产可用”。老师按真实提交逐项验收，再安排未公开变式考试。

## 单页速记

- 一个完整用户路径优先于堆技术名词。
- 每条需求绑定当前 commit 的合适证据。
- 证据元数据可检查，内容仍需审阅。
- AI 可以写代码，判断、解释、排错与责任需要你掌握。
