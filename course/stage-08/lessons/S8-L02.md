# S8-L02｜系统设计与陌生故障答辩

教材状态：已编写，可提前学习；不代表学习者已作答或通过考试。
阶段：08 毕业项目与求职表达。先修：前序项目、真实接入与可复现证据。
建议投入：35–60 分钟 + 项目练习。允许 AI 协作，要求本人解释与验证。

## 本课目标

- 按约束而不是组件名设计
- 建立从症状到证据的排错顺序
- 用取舍回应面试追问

## 1. 按约束而不是组件名设计

先澄清用户规模、延迟/费用目标、数据权限、任务时长、可恢复性和部署条件，再选择服务、队列、存储、检索与模型。为每个组件说明它解决哪个问题、引入什么成本、何时可以删掉。设计图里还应出现失败、取消与信任边界。

## 2. 建立从症状到证据的排错顺序

面对“助手突然答错”，先复现并锁定版本/输入，再查权限与数据、候选证据、Prompt/模型完成、工具结果和 UI 状态。一次只改能解释证据的最小范围，再跑回归；不要同时换模型、重建索引、重写前端而无法归因。

## 3. 用取舍回应面试追问

解释为什么选 TS 主线、Python 桥接放在哪里、何时用 MCP、何时不用多 Agent。给出替代方案、负面影响和触发迁移的指标。对没验证的吞吐、用户规模或生产效果直接说明边界，并提出验证计划；不能把课程模拟故障包装成商业系统事故。

## 动手验证

先写预测，再运行，最后修改一个条件观察反例。不要把网页机制演示当成真实基础设施验证。

## 实验：一次只改变一个主要因素

先预测输出，再运行并修改一个条件。这是教学用的 JavaScript 机制演示，不是真实模型、数据库、协议 SDK 或生产系统。

~~~js
const before={model:"A",prompt:"v1",index:"i1"};
const after={model:"A",prompt:"v2",index:"i1"};
console.log("变化字段",Object.keys(before).filter(k=>before[k]!==after[k]));
console.log("单因素对照仍需同集输入、评分和足够样本");
~~~

观察方向：只变化 Prompt 版本；仍需实际执行才能对结果做因果判断。

提示：配置对照不是结果证据。

先写你预期的行为，再让 AI 协作实现。提交具体 commit、输入、预期、实际、命令、失败复盘与未验证项；本教材不代做学习者项目。
