## 1. 系统设计先问哪些约束

先明确用户、任务、数据敏感性、写操作、规模、延迟和成本上限，再画数据流。比如“企业知识助手”与“自动执行退款助手”的风险和状态要求完全不同。

设计按请求进入、身份校验、任务持久化、检索、模型、工具执行、结果与观测展开。每条箭头说明传什么、谁可信、失败后谁重试、是否有副作用。先给简单基线，再解释需要队列、MCP 或多角色的具体原因。

## 代码阅读：用同一组事件比较错误与修复

### 先复现错误

reduceWithoutGuards直接把事件覆盖到状态，意味着任何任务、任何版本、任何终态后的消息都能更新页面。eventSequence故意包含旧任务、高版本旧结果、重复中间态和终态后的错误事件。

reduceWithGuards只做三件事：runId不符就拒绝，版本不递增就拒绝，当前已终止就拒绝。全部通过才读取事件字段更新状态。

|事件|是否接受|理由|
|---|---|---|
|new版本1中间结果|接受|当前任务且版本更新|
|old版本9完成|拒绝|属于旧任务，高版本也不能混用|
|new版本2完成|接受|当前任务合法推进|
|new版本1重复|拒绝|版本旧|
|new版本3运行中|拒绝|版本虽新但当前已终止|

### 修复结论要限定范围

最终保留新任务版本2的答案，证明这组UI事件重放符合规则。它没有向上游发送取消，也没有验证后台费用；不能把“页面不被覆盖”说成“所有旧工作已停止”。

### 带提示的练习

先只保留一个守卫，看哪些错误仍会发生。再为你自己的项目增加当前版本未知事件，判断应忽略、报错还是拉取快照。面试叙述按症状、复现、假设、证据、最小修复、回归与边界展开。

## 2. 一个公开故障：旧结果覆盖新任务

用户第一次查询慢，点击取消后开始第二次查询。第一次结果晚到，覆盖了第二次页面。先预测：只在按钮上设置 loading=false 能修好吗？

### 完整实操文件：S8-L02.mjs

~~~js file=S8-L02.mjs
// 先复现无保护 reducer，再用任务ID、版本和终态三个条件拒绝错误事件。
import assert from "node:assert/strict";
const initialState = { runId: "new", version: 0, status: "running", text: "" };
const eventSequence = [
  { runId: "new", version: 1, status: "running", text: "新任务中间结果" },
  { runId: "old", version: 9, status: "succeeded", text: "旧任务答案" },
  { runId: "new", version: 2, status: "succeeded", text: "新任务最终答案" },
  { runId: "new", version: 1, status: "running", text: "重复中间事件" },
  { runId: "new", version: 3, status: "running", text: "终态后错误事件" },
];
const reduceWithoutGuards = (previousState, event) => ({ ...previousState, ...event });
// 只接受当前任务、更高版本、未结束时的事件。
function reduceWithGuards(previousState, event) {
  if (event.runId !== previousState.runId || event.version <= previousState.version) {
    return previousState;
  }
  if (["succeeded", "failed", "cancelled"].includes(previousState.status)) {
    return previousState;
  }
  return {
    ...previousState,
    version: event.version,
    status: event.status,
    text: event.text,
  };
}
const brokenResult = eventSequence.reduce(reduceWithoutGuards, initialState);
assert.equal(brokenResult.text, "终态后错误事件");
const guardedResult = eventSequence.reduce(reduceWithGuards, initialState);
assert.deepEqual(guardedResult, {
  runId: "new",
  version: 2,
  status: "succeeded",
  text: "新任务最终答案",
});
assert.equal(
  eventSequence.slice(0, 2).reduce(reduceWithGuards, initialState).text,
  "新任务中间结果",
);
assert.equal(
  eventSequence.slice(0, 2).reduce(reduceWithoutGuards, initialState).runId,
  "old",
);
console.log("broken replay reproduced old-result overwrite and terminal regression");
console.log(
  "guarded replay kept new run/version 2/succeeded; upstream cancellation unverified",
);
~~~
~~~text expect=S8-L02.mjs
broken replay reproduced old-result overwrite and terminal regression
guarded replay kept new run/version 2/succeeded; upstream cancellation unverified
~~~

**选做本地验证：**运行 npm run tutorial -- S8-L02。修复同时检查 runId、版本和终态，但它只保护界面结果。第一次网络请求、模型与工具是否实际停止，需要 S1/S3 的取消与服务端资源证据。面试时说清局部修复的边界，比宣称“已经解决全部取消问题”准确。

## 3. 一次排错应如何叙述

先描述用户可见症状与最小复现；列出可能层级；从 trace、事件、请求与数据库中缩小范围；提出一个可证伪假设；改最小边界；重放原失败和相邻条件；报告剩余不确定性。

不要先大改整个架构。若证据显示旧任务回调覆盖 UI，先修任务关联与终态；若服务端仍产生重复写，再沿副作用幂等和租约继续查。每个结论都对应证据。

## 4. 公开练习题

- 任务点击取消后仍扣费：列出客户端、服务端、上游与计量四层证据。
- 两个 Worker 都发送回复：画租约、token、幂等与外部发送边界。
- RAG 引用是真的但答案错误：区分召回、条件遗漏与语义支持。
- 平均质量提高但企业用户投诉：检查切片、关键错误与失败分母。
- MCP 本地能用、远程403：先核对身份、受众、scope、传输与服务日志。

这些题只给分析方向。回答时先说你需要什么证据，再做最小实验，不要把每个问题都回答成“换更强模型”。

## 项目迁移与考试方式

给自己的项目准备一次8分钟演示和一次20分钟故障排查。老师会从你提交的 commit 出发改一个输入、打断一次依赖或制造版本竞争，要求你解释影响、定位并验证。理论问答由你独立作答，AI 协助范围照实记录；无法技术监考，不伪称独立能力已认证。

通过标准沿用考试蓝图：概念、项目变更与排错分别评分，关键越权和不可控副作用不能靠其他得分补足。未通过只补薄弱点，再用等难度新变式复测。

## 单页速记

- 系统设计从约束与数据流开始。
- 排错用可证伪假设与最小复现。
- 局部验证说明边界，不把 UI 修复当上游取消。
- 正式考试考迁移与未知故障，不背公开题输出。
