## 本课目标

- 先写评分规则再看结果
- 区分确定检查与模型评分
- 做配对回归而非选最好样例

## 1. 先写评分规则再看结果

工单分类可以有标签，引用有支持性要求，工具调用有允许/拒绝规则，不同任务不能用同一个模糊“智能程度”打分。为正常、边界、攻击和无法完成的输入分层，保留开发集与最终测试集。自动评分器是测量工具，也需要用人工样例检查误判。

## 2. 区分确定检查与模型评分

JSON 结构、权限边界和最大工具数适合程序断言；摘要忠实性等可能需要人工或模型辅助判断。模型裁判存在偏好与噪声，不能单独证明安全正确，尤其不应让它与被测系统共享未经核验的结论。报告规则、裁判版本与人工抽检范围。

## 3. 做配对回归而非选最好样例

保存输入、版本、期望与真实输出，对同一案例比较改动前后。质量、关键错误、成本和延迟一起评估；事先设定阻断阈值。此课程采用本地可导出的评测格式，不绑定某家托管 Evals 平台生命周期；服务 API、SDK 与产品状态须在真实接入时重新核查。

## 动手验证

先写预测，再运行，最后修改一个条件观察反例。不要把网页机制演示当成真实基础设施验证。

## 实验：平均分掩盖关键错误

先预测输出，再运行并修改一个条件。这是教学用的 JavaScript 机制演示，不是真实模型、数据库、协议 SDK 或生产系统。

~~~js
const results=[{score:1,critical:false},{score:1,critical:false},{score:0.9,critical:true}];
const average=results.reduce((s,x)=>s+x.score,0)/results.length;
console.log({average,canRelease:!results.some(x=>x.critical)});
~~~

观察方向：平均分很高，但关键错误阻断发布。标签是合成教学数据。

提示：业务硬约束不必被平均分抵消。
