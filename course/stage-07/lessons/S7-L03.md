## 本课目标

- 建立可复现的发布单元
- 把容量与费用当约束
- 设计发布、回滚与故障演练

## 1. 建立可复现的发布单元

锁定依赖与运行时，区分构建时配置和运行时密钥，提供数据库迁移、健康与就绪检查。容器镜像不应包含 .env 或开发目录，使用适当用户和最小运行权限。Dockerfile 能构建不等于服务可用；需要从干净环境按文档启动并验证。

## 2. 把容量与费用当约束

为每用户、租户和上游设置合理并发与速率限制，避免重试风暴。排队要有上限与超时，超过容量时明确反馈。降级可以切换受控模型或只返回检索证据，但不能把缓存旧结果标成新生成成功，也不能绕过权限或关键验收规则。

## 3. 设计发布、回滚与故障演练

发布前跑回归，发布后检查错误、延迟和业务指标；保留可回滚版本及迁移兼容计划。模拟服务商故障、数据库不可用、资源超限和进程退出，验证何时重试、何时拒绝、怎样恢复。课程不直接替学习者部署到公网；先提交本地可复现实测与部署方案。

## 动手验证

先写预测，再运行，最后修改一个条件观察反例。不要把网页机制演示当成真实基础设施验证。

## 实验：队列也需要容量上限

先预测输出，再运行并修改一个条件。这是教学用的 JavaScript 机制演示，不是真实模型、数据库、协议 SDK 或生产系统。

~~~js
const max=2;
let queued=0;
for (const id of [1,2,3,4]) {
 if (queued>=max) console.log(id,"拒绝/提示稍后重试");
 else {queued++;console.log(id,"已入队");}
}
console.log("内存示例，不是分布式限流");
~~~

观察方向：前两个入队，其余被明确拒绝；生产需跨实例计数和退出/超时处理。

提示：无限队列把拒绝变成更晚、更贵的失败。
